# 架构选型

在主流程第 2 步使用。先判断是否需要大语言模型，再选择控制方式，最后判断是否需要多个 Agent。任务复杂、步骤多或工具多只是线索，是否用多 Agent 另行判断。

## 1. 先排除不需要 Agent 的情况

按下表检查，命中时优先采用更简单的处理方式。

| 情况 | 优先做法 |
|---|---|
| 规则明确，普通代码、SQL 或现有系统就能达标 | 用普通代码；说明理由，结束 Agent 设计，Agent 章节无需填写 |
| 输入材料已给齐，只需要分类、抽取、改写或总结 | 先试单次模型调用，必要时由代码预先检索材料 |
| 步骤、分支和失败处理能预先定义 | 固定工作流，步骤多也照样用工作流 |
| 原始目标、评价标准或工具权限不明确 | 先澄清；信息不足时补信息，自主探索只用于真实的未知 |
| 错误后果不可接受，又无法验证或拦截关键操作 | 保留人工判断，模型只做辅助；增加 Agent 数量解决不了这个问题 |

单次调用也可以有检索、示例和结构化输出。固定工作流也可以有条件分支、并行步骤和有上限的重试；有这些能力的流程仍由代码控制执行。

## 2. 分开判断控制方式与协作结构

### 控制方式：下一步由谁决定

| 方式 | 判断标准 | 适用信号 |
|---|---|---|
| 单次调用 | 模型一次生成结果，前后处理由代码完成 | 已有足够输入，一次处理能达标 |
| 固定工作流（Workflow） | 路径、分支规则和循环边界预先写入代码 | 能清楚列出处理步骤及异常路径 |
| 模型自主决策（Agent） | 模型根据观察结果选择下一步行动，并可能修订计划 | 搜索、诊断、探索的下一步难以预先确定 |

模型给输入分类后由代码选择已定义的分支，仍然可以是工作流。模型一次生成计划、再由代码执行，也可能仍是工作流；判断标准是执行时是否持续根据反馈决策。

### 协作结构：一个还是多个任务单元

| 控制方式 | 单任务单元 | 多任务单元 |
|---|---|---|
| 固定工作流 | 按固定路径调用模型或工具 | 固定顺序或并行执行多个任务角色，包括框架中的多个 LLM Agent |
| 模型自主决策 | 一个 Agent 自主处理任务 | 多个 Agent 分工，整体编排和各 Agent 内部可以分别采用不同控制方式 |

本 Skill 沿用「提示词、工作流、单 Agent、多 Agent」四个常用标签，四个标签描述的维度不同：「工作流」描述控制方式，「多 Agent」描述协作结构，二者可以同时成立。

在设计文档里写明两者，例如「工作流：固定顺序，3 个任务角色」或「单 Agent：局部自主决策，外层由工作流控制」。固定工作流中的多个模型节点按任务契约定义，规划、记忆和自主循环按需配置。

不同资料对 Agent 的命名范围不同。本 Skill 允许按框架命名描述多个 LLM Agent，但必须注明自主决策边界；自主协作能力以实际的决策方式为准，角色名称只是名称。

## 3. 用 C.U.P. 描述需求，不机械打分

C.U.P. 是课程中的选型启发式：复杂度（Complexity）、不确定性（Uncertainty）、性能约束（Performance Constraints）。它是定性框架，没有可以直接计算架构的分数或阈值。

| 维度 | 要回答的问题 | 对选型的作用 |
|---|---|---|
| 复杂度 C | 输入是否多轮、多模态或很长？依赖哪些工具和数据？步骤及依赖关系有多少？ | 决定是否分步骤处理；是否需要 Agent 还要结合其他维度 |
| 输入不确定性 U | 请求类型和输入质量是否变化？是否可以限制支持范围或先分类？ | 优先考虑澄清、预处理或路由，再考虑提高自主性 |
| 过程不确定性 U | 下一步能否预先定义？是否必须根据新证据改变策略？ | 判断是否需要模型自主决策的主要信号 |
| 目标不确定性 U | 什么算完成？输出好坏能否检查？ | 先明确评价标准；目标模糊时先澄清，Agent 数量另行判断 |
| 性能约束 P | 时延、单次及总成本、调用量和有效上下文预算是多少？ | 判断候选方案是否可行，在选型时就要考虑 |

不确定性三维度来自课程的「业务熵」表述。本 Skill 将其作为定性问题使用，没有计算熵值，Agent 数量也与阿什比定律无关。

| 需求特征 | 首先尝试 | 不能直接推出的结论 |
|---|---|---|
| 任务简单，路径明确 | 普通代码或单次调用 | 反思、规划或工具按需加入 |
| 步骤较多，路径明确 | 固定工作流 | 步骤多只是线索，多 Agent 另行判断 |
| 必须根据反馈决定下一步 | 单 Agent 或工作流中的局部 Agent | 输入开放时，执行路径仍可固定 |
| 依赖多，路径也不确定 | 先检查单 Agent 的瓶颈，再考虑拆分 | 高 C、高 U 时仍先比较单 Agent |

## 4. 按最简单可行方案逐步选择

1. 用普通代码或现有系统作为基线。能满足需求时停止升级。
2. 如果需要语言理解或生成，先试单次调用。检查输入是否齐全、输出是否可校验。
3. 单次调用不足，但可定义固定步骤时，选择工作流；只增加解决已知失败的步骤。
4. 只有某个环节需要根据反馈探索时，将自主 Agent 限制在该环节，其余流程由代码控制。
5. 自主任务默认先用一个 Agent。只有出现第 5 节的具体拆分理由时才考虑多个。
6. 对候选方案做性能约束检查，记录收益、代价及未验证项；约束不满足时收缩范围、降级或保留人工流程。

缺少试验结果时，可以给出「候选选型」，但必须写明待验证的瓶颈和最小验证动作。设计推演与性能实测分开表述。

## 5. 什么时候值得拆成多个 Agent

拆分是为了解决一个任务单元难以承担的具体问题。下面的隔离需求只构成候选理由，拆分前仍需与简单做法比较。

| 候选理由 | 先尝试的更简单做法 | 值得拆分的信号 |
|---|---|---|
| 上下文或记忆不同 | 按需检索、清理工具结果、压缩、结构化笔记 | 不同子任务需要独立探索，细节会挤占主任务上下文，且可通过产物交接 |
| 工具或工作方法不同 | 工具分组、按需加载、复用 Skill | 同时暴露工具或不同指令持续导致误选、冲突，隔离能明确改善 |
| 权限不同 | 工具层权限控制，读写分离 | 研究、执行、验证需要不同权限边界，独立运行身份有实际价值 |
| 生成与评审关注点不同 | 优先运行测试或确定性校验，必要时另一次评审调用 | 独立评审上下文与任务契约有价值；「审核员」这个名称本身不构成理由 |

检查子任务能否独立完成、输入输出是否清楚、交接是否会丢失关键信息。子任务紧密依赖同一份实时状态时，先考虑单 Agent 或明确的共享状态工作流。

并行是执行方式，与多 Agent 是两回事。固定独立子任务可以由代码并行调用；只有同时需要角色、上下文或权限隔离时，才进一步考虑 Agent 拆分。

融合旧 coordinator 的复杂度速判时，只保留「简单任务直接做、跨模块先调查、独立问题可并行」的原则。文件数量、模块数量只帮助估计阅读工作量，创建 Agent 另按隔离理由判断。

## 6. 性能约束与混合架构

| 检查项 | 要记录什么 |
|---|---|
| 时延 | 最长依赖链、模型与工具调用、校验、重试及人工等待；依赖链耗时在并行后依然存在 |
| 成本 | 所有分支的模型输入输出、工具费用、重试和评审；并行后总调用成本通常不变 |
| 上下文 | 每步实际需要的信息和工具定义；每次加载量按需求计算，与文件总量无关 |
| 可控性 | 模型能自主决定什么，哪些操作由代码限制或必须人审 |

先估算，再用代表性输入测量。已有明确硬约束而估算超限时，方案标为不可行；尚未测量或约束缺失时，标为待验证、待确认，数值只写实测值或标明的估算值。

约束不满足时，可选择限制支持范围、预先整理材料、采用固定工作流、只在局部启用 Agent，或转人工。收缩能力边界需要用户确认，并写明不支持的情况。

混合架构是「工作流骨架 + 局部自主决策」。例如诊断任务先按固定步骤收集监控和日志，再让单 Agent 在限时、只读范围内选择补充检查；超时则返回已有证据给人，高风险处置由人决定。

混合是一种组合方式，四个标签之外没有第五个等级。时延、上下文和安全问题要分别解决，增加 Agent 数量帮不上忙。

## 7. 写出可评审的选型结论

将结论写入现有设计文档第 2 节，沿用其中的字段，按下表填写：

| 字段 | 必须包含的内容 |
|---|---|
| 选定档位 | 常用标签、控制方式、任务角色或 Agent 数量；自主决策具体位于哪里 |
| 选择理由 | 与需求对应的路径、依赖或隔离证据；C.U.P. 只写影响决策的部分 |
| 为什么不选更简单的一档 | 更简单候选的具体不足；已选最简单方案时写「无须升级」 |
| 性能约束校验 | 用户约束、估算或实测依据、是否满足；未知项标为待确认或待验证 |
| 主要风险 | 未覆盖输入、交接损失、自主越界等实际风险及兜底方向 |

无需在每次设计中强行比较所有组合、列全 21 种模式或选定框架。只论证当前方案相对更简单候选的必要性。

## 8. 边界案例

| 场景及前提 | 候选选型 | 关键理由 |
|---|---|---|
| 按已确定规则计算价格、校验必填字段 | 普通代码 | 没有必须由模型承担的语言理解或生成任务 |
| 已提供文本和分类定义，只需判断类别 | 单次调用 | 一次处理即可候选达标；反思、规划和多 Agent 都用不上 |
| 工单分类并回复固定常见问题，分类与知识来源明确 | 固定路由工作流 | 请求内容变化，但处理路径已定义；未知类别转人工 |
| 同一客服需要多轮查询不同系统，并根据结果选择下一步 | 单 Agent，外层保留权限与升级规则 | 过程不确定才是自主决策理由；「客服」这个名称本身不决定选型 |
| 生成代码、审查、重构，顺序固定 | 固定工作流，3 个任务角色或 LLM Agent | 固定顺序也可以用多个 Agent；重构必须同时读取原代码和审查意见 |
| 大量独立文档按固定格式抽取并汇总 | 并行工作流 | 文档多可以分片，自主 Agent 和协调者按需引入 |
| 跨领域研究，搜索路径不确定且需分别深入探索 | 多 Agent 候选 | 独立探索与上下文隔离可能有价值；仍须验证交接质量和预算 |

代码流水线的选型结论示例：

- 选定档位：工作流；代码固定编排 3 个任务角色，没有自主规划循环。
- 选择理由：生成、审查、重构的顺序已知，审查任务采用独立输入与评价标准，输出以契约交接。
- 为什么不选更简单的一档：需求明确要求独立审查与定向修改，单次生成不能交付该过程；质量是否优于单次调用尚未实测。
- 性能约束校验：至少包含 3 次模型调用，校验和重试会增加开销；用户预算待确认、实际时延待测量。
- 主要风险：审查意见不可靠或重构丢失原始约束；重构输入保留原始目标、生成代码与审查意见，结果再做可执行校验。

## 9. 反模式与来源

- 用「高复杂度、高不确定性」直接决定多 Agent，未检查单 Agent 的具体瓶颈。
- 为已有固定流程增加自由规划，扩大原本可以限制的执行路径。
- 因输入开放或目标模糊就增加 Agent，跳过澄清、路由和评价标准设计。
- 每个步骤都建立长期角色、记忆和工具箱，或按文件数量机械派发 Agent。
- 为节省成本悄悄删减用户需求，或者把估算、场景推演写成实测结果。
- 为了显得完整而补齐不需要的模式；没有工具或反思就判设计低分。

主要依据：Anthropic《构建有效的智能体》（Building Effective Agents）、Google ADK《顺序工作流智能体》（Sequential template workflow agent）、Anthropic《智能体的有效上下文工程》（Effective Context Engineering for AI Agents）、《企业级多智能体设计方法论精粹》第 01、04、05、25 课，以及旧 coordinator 的复杂度速判。

上述两维度选型、候选验证及隔离判断是本 Skill 的工程归纳。课程的 C.U.P. 和「熵」只作定性参考；课程中「每个 Agent 必须自主决策」及按高 C、高 U 直接选择多 Agent 的说法只适用于课程语境，本 Skill 另作定义。
