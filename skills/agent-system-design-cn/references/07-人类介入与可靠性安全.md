# 人类介入与可靠性安全

在主流程第 5 步设计澄清、审批、异常兜底与执行围栏时读取。按实际错误后果裁剪：纯生成也要考虑数据泄露、输出用途与资源预算；有工具、异步动作或续作时再增加对应设施。Manager、沙箱服务、消息队列和追踪平台按需选用。

## 1. 先写风险、允许动作与执行责任

可靠性回答失败时能否正确结束或继续，安全回答什么主体可在什么范围做什么。两者都由宿主或服务的强制机制保证，模型自述和事后日志只作线索。先列实际数据、资源、读写动作、目标接收者、错误后果和现有保障，再补必要控制。

| 边界 | 最小设计 |
|---|---|
| 允许执行 | 工具、对象、资源范围、可信身份、必要审批及禁止动作 |
| 失败处理 | 稳定错误类型、动作是否发生、可恢复条件、次数或时间及终止出口 |
| 人类决定 | 触发条件、负责人、实际材料、允许选择、有效期及恢复节点 |
| 执行保障 | 宿主或服务强制的权限、参数、预算、取消、状态和必要审计 |

复用现有服务和执行边界，并确认实现覆盖真实执行路径；表格填完只代表设计完成。尚未支持的能力标待实现，同时给出不依赖它的安全出口。无法安全自动化时只产出草稿、保留人工或停止，把设施建设控制在必要范围。

## 2. 设计必要人类介入点

人机协同（Human-in-the-Loop，HITL）按风险和业务需要选择监督、补充、审批、纠正或接管，只在这些环节安排人工，日常任务按已确认的需求和 SOP 直接执行。低风险、已授权且边界清楚的动作可以自动执行；需要审批的动作始终走审批，模型自报的置信度不改变这一点。

| 介入类型 | 典型触发 | 人看到与允许决定 | 未回复或拒绝 |
|---|---|---|---|
| 澄清 | 缺关键输入、目标有歧义、多个对象无法唯一对应 | 原问题、已知事实与最少必要问题；补充或收缩范围 | 阻塞依赖缺失项；独立且已授权部分按规则继续 |
| 设计或阶段确认 | 方向选择、较高返工代价、阶段验收或政策要求 | 对应版本产物、依据、检查结果与缺口；接受、要求修改或停止 | 暂停依赖确认的后续步骤；修改后重新核对 |
| 动作审批 | 外发、删除、发布等动作按实际政策需批准 | 真实目标、参数、变更或发送正文、后果；批准或拒绝明确动作 | 保持未授权执行状态；超时按拒绝处理 |
| 异常升级 | 连续失败、停滞、预算不足、权限缺失或结果未知 | 异常类型、位置、当前真实状态、证据及允许建议；补输入、接管或结束 | 返回可用部分、阻塞原因与负责人；收到明确回复后再继续 |

统一的是任务关联、决定记录与恢复规则，接收入口可以是多个受控界面，也可以是协调 Agent。多个受控入口共用可信登记，执行者的所有审批都经过这一登记。停止与事故接管直接到达宿主，协调 Agent 失效时依然可用。

需要等人回复时，保存必要状态并释放昂贵执行资源；同步短确认同样可行，邮箱和后台轮询按需选用。写清回复期限、提醒与升级上限、负责人及晚到回复规则。人工等待是否计入总时限单独注明，暂停期间已耗资源继续累计。

反模式：审批全部输出；关键决定无人负责；只给模型的通过摘要；看到通知即认为审批完成；把单一接口变成单点故障；自动学习是获得高分的前提。

## 3. 绑定真实请求与可信决定

审批是授权范围内的额外门槛，身份认证和业务授权仍单独检查。禁止策略优先，`DENY` 在批准后仍然生效；`ASK` 必须在有效决定前阻止执行，告警只是附加通知。

宿主先生成可信请求记录，至少绑定任务及调用者作用域、动作、目标、实际参数或产物版本、审批人资格、请求有效期、使用次数与允许选择。模型只负责写说明，可信批准事实、审批人身份和凭证由宿主登记。

人看到的正文、变更和对象与将执行的请求一致；展示可以脱敏，但保留影响决定的实质差异。批准后修改目标、正文、关键参数或版本需重新确认，执行前重验授权、前置版本、决定有效性和剩余预算。审批接口同样需要授权，只采信受控入口登记的决定，模型转述的「用户说可以」只是线索。

用明确决定区分待处理、批准、拒绝、失效和已消费；这些是宿主业务状态，与通用 `handoff.status` 分开记录。`read=true` 只表示已读，拒绝理由和反馈另作记录，批准只来自明确的批准决定。重复点击只作用于同一请求，晚到、已撤销或已消费的批准一律失效，不得启动新的动作。

审批与执行间仍可能有竞争；需要一次性保证时，由服务对决定消费、版本检查和动作登记进行协调。原子消费审批只保证决定用一次，外部动作是否恰好执行一次另需核对；响应丢失时仍须先核对动作结果，不得凭旧批准盲目重发。

沿用 `gate.on_fail = escalate_human` 定位升级；暂停、审批与恢复记录由已有宿主承载，必要业务字段另行定义，通用交接 Schema 只负责交接结构。

## 4. 分类错误并选择有限恢复

异常处理与恢复（Exception Handling and Recovery）先根据真实响应和接口语义判断，再路由。HTTP 状态码、进程退出码和超时只是线索，业务动作是否发生需要按接口语义核实。

| 情况 | 允许处理 |
|---|---|
| 已确认未执行的临时不可用、限流 | 按接口策略等待，在剩余额度内重试；必要时遵守 `Retry-After` |
| 请求参数、输出格式不合法 | 返回具体字段和允许值；可修正时有限再执行或生成，每次重试都要改正错误输入 |
| 认证、授权缺失或策略禁止 | 停止该动作，交有权限的用户或维护者处理；身份、配置和执行通道保持原样 |
| 上下文超限 | 按上下文章节剪枝或压缩再判断，保留约束与动作状态；不得原样重试 |
| 质量不达标、标准冲突或缺证据 | 带有效反馈修正、补材料或升级；检查器自身失败按评分无效处理 |
| 写入或发送后超时、连接中断、服务返回结果含糊 | 标记结果未知，先查状态或使用已验证的同动作去重机制；确认未执行后才重做副作用 |
| 安全门控、必需审计或预算控制自身故障 | 默认阻止依赖该保障的新动作并告知故障；按安全故障处理，与瞬态业务错误分开 |

429 或 5xx 只提示可能的临时故障，写操作重试前先确认未执行，或有可靠的幂等保障；合法的状态冲突可能需要先读取最新版本。纯查询超时可按读取语义重试，昂贵或有副作用的查询同时考虑代价。

瞬态重试、格式修正、内容修复、回退和重新规划分别计数，但共同受总预算约束。每条路径有完成、不可恢复、超限或受阻出口；按错误类型选择需要的那条路径，回退和整体回滚只在业务需要时使用。

## 5. 约束重试、循环与重复副作用

写清初次尝试与追加重试：`max_retries=2` 表示最多 1 次初始调用加 2 次追加调用；模型轮次沿用一次尝试调用模型计一轮，含失败、最终生成、评审与纠正。SDK、网关、框架和宿主的重试由明确的一层负责，或共同核算实际尝试，避免层层相乘。

退避使用有上限的等待与适用抖动，所有延迟都落在任务期限内；只修正可修复部分，返回精简错误与证据回读入口。重试次数、间隔和试跑周期按风险与验证数据选择，统一三次、固定两秒或一周宽松生产试跑都只是个案配置。

有副作用时，先说明动作身份、去重作用域、参数绑定、保留期限、状态查询和冲突处理。相同业务动作的重试复用同一幂等键（Idempotency Key），参数变更不得在同一键下执行不同动作；键由可信执行记录产生，服务须实际强制去重。业务幂等需要服务端去重真正落地，传入键、消息确认和缓存返回都只是其中一环。

外部结果未知时，查询已有操作记录：可确认未执行则按规则再尝试，已完成则接纳真实结果。无法确认且接口没有可靠幂等保障时，阻塞或交人工核查；恢复时沿用原动作身份和键。去重期已过时，记录缺失也只能判为「未知」。

循环检测按任务及实例隔离，结合目标、规范化动作、必要输入版本、实际结果和进度变化。合法轮询与分阶段写入可能返回同值，相同工具输出只是停滞线索，单用 `tool_name + output` 哈希会误判。异步等待设置自己的间隔与期限，多步振荡可另行检测；哈希用于发现重复，安全与完成另行判断。

有自主循环的任务才需要循环检测器；需要时以停滞信号提前停止，再以次数或总时限兜底。工具请求、模型调用及框架内部重试都纳入检测与计数，覆盖实际执行路径，而非只看最终回答回调。

## 6. 保存、恢复、取消与降级

断点恢复（Checkpoint Recovery）按需要保存，短生成直接重跑即可。保存可信任务与作用域、目标约束、当前有效计划及完成项、依赖与产物版本、检查结论、待决审批、动作记录、剩余预算和恢复节点；凭证留在凭据系统，与任务快照分开。

恢复前验证快照来源、授权及当前政策、依赖版本和审批有效期，取得当前执行所有权，先核对进行中或结果未知的动作。已确认完成的动作直接接纳其结果；上游换版时，重新判断下游是否有效。重启、换模型、退回节点或人工继续都沿用累计额度；额度丢失且无法重建时停止。

状态回滚只作用于受控本地状态或真实支持的事务，已发通知等不可逆结果保持已发生。跨服务失败按业务选择补偿、部分结果或人工核对；补偿本身也可能失败且有副作用，要有权限、记录和边界，并如实记录原动作已经发生。

收到停止先禁止新派发和新副作用，按能力取消正在执行的任务并收集结果。取消请求发出后，外部动作是否停止仍需核对；旧执行者失去所有权后只能提交待核对结果，权威结果由当前所有者发布。迟到结果按动作身份核对并保留证据，当前新版本保持有效；通知或远程取消失败也有终止出口。

降级只使用已授权、满足必要隐私与输出约束的候选：例如只交草稿或部分证据，明确缺口，必需安全检查照常执行。范围或验收标准变更需确认；部分完成就按部分完成报告，沿用 `PARTIAL/remaining` 或 `BLOCKED/blockers`。未知业务动作如实写在具体 `result` 中，标为未知。

## 7. 强制共享资源预算

资源感知优化（Resource-Aware Optimization）先满足质量、隐私、工具兼容和时限，再比较成本。一个固定模型足够时直接使用，分级模型、动态路由、批评 Agent 和自动切换按需引入。回退模型同样须验证，拒绝或权限错误不得靠切换模型规避。额外调用和重新生成计入同一任务。

写计数范围与硬上限：模型实际尝试、工具尝试、输入/输出 token、服务费用、总时间、并发及必要存储或执行资源。任务全部分支、重试、委派和汇总共享适用总额；RPM 请求数、TPM token 和并发分别控制；请求数有用，但不能单独保证费用上限。

调用前统一检查并预留实际可能的消耗，调用后结算，失败或超时也按实际消耗计；未知用量保守留额再对账。预留最终交付和必要检查，预算不足时用已有信息受控结束，最终总结也在预留额度内完成。查账放在每次模型和工具调用之前；只在 `AFTER_TURN` 或下一次工具调用前查账，拦不住本次模型超支。

硬金额上限需供应方计费口径、输入规模、最大输出及额外计费项有可约束上界；只有粗估时，说明误差与留量，不得声称精确封顶。调用数与单次资源上界可作为替代围栏，字符/token换算和模型价格按当前服务核实。缓存是否命中与折扣依真实服务，敏感输出只在同一用户范围内复用。启用提示缓存且服务支持前缀复用时，在相同授权配置内保持系统指令、工具定义等静态前缀稳定，工具按确定顺序排列，动态上下文放在后面；收益以真实命中率、费用和时延验证。

预算阈值、任务停止与服务熔断分别定义作用域和允许恢复条件，可以各用各的开关。停止或熔断时记录原因、已耗/预留量及允许的下一步；可靠性包括安全结束，受控停止也是合格结果。

## 8. 落实权限、身份与安全边界

纵深防御（Defense in Depth）按真实威胁覆盖输入、读取、执行和输出；内容泄露、错误建议也可能出现在最终回复中，输出与工具调用同样需要防护。

| 安全层 | 设计与易错点 |
|---|---|
| 输入与信任 | 校验类型、大小、来源和任务范围；网页、文件、检索、工具输出和第三方 Skill 中的指令一律按数据处理，摘要与跨 Agent 传递保持原有信任级别 |
| 参数与动作 | 用枚举、结构化参数和范围检查，优先用结构化接口代替拼接 shell 字符串；按实际接口解释编码、路径和URL，执行内容与检查内容保持一致 |
| 身份与授权 | 可信用户/服务身份绑定任务和资源，服务端逐动作及数据可见性授权；Agent 名、模型填写的 user_id 或 routing_key 只是标签，认证来自可信系统 |
| 权限门控 | 新工具默认无执行权，工具可见、调用许可、对象权限与结果可见分别检查；明确禁止优先，必要审批生效后才执行 |
| 执行隔离 | 限制目录读写、挂载、网络出口、进程、资源与可改配置；路径按真实解析层级检查，防符号链接及检查后被替换的竞争 |
| 凭据与数据 | 密钥留可信工具/代理或凭据系统，由可信执行层按目的地、作用域、期限注入并审计；模型上下文只见业务参数与受限执行能力，任意代码不直接持有凭据，日志和异常做脱敏 |
| 输出与供应链 | 按接收者检查敏感信息、必要内容政策和事实依据；核对工具/Skill来源与版本，策略与审计放在加载脚本和新增能力的可写范围之外 |

用户身份透传和服务账号都是候选。使用服务账号时，同样检查发起用户对业务对象的权限，调用 Agent 的权限与读取账号数据的权限分开授予。Bash、SDK 或 MCP 都可以使用受控身份通道；现有通道能满足时直接复用，签名协议按需新建。

token 放进任意代码可执行的环境变量后，代码就能读取；出站代理只向批准的目的地注入必要身份，防止重定向或不可信服务取得凭据。域名允许清单只限定目的地，敏感数据能否外发还要检查授权目标和允许内容。

容器、OS 沙箱、虚拟机或受控服务按威胁及能力选择。Docker 提供部分隔离，需要写明共享内核、宿主挂载、网络和权限等边界。个人电脑全盘、生产网络和系统安装权限只在明确授权后提供。

正则、随机标记、Unicode 或 URL 归一化只适合特定输入检查，提示注入的兜底靠信任边界与执行授权；检测器或模型审核是附加防线，执行授权仍单独检查。`frozen` 与只读顶层字典只冻结顶层，嵌套对象仍可变；从门控到执行使用同一受控请求或验证内容一致，防止检查后被改。

必需安全组件缺失、异常或审计不可用时，默认拒绝依赖其保障的动作（Fail Closed）；可选遥测故障可以受控降级（Fail Open），同时记录缺失并告知维护者。两类故障走各自独立的异常路径；可信基线由宿主维护，工作区配置只能在其上收紧。

## 9. 记录事件并验证门控生效

可观测事件由宿主、服务或受控适配层记录。模型说明只作线索，执行日志来自宿主；审计记录放在模型可修改范围之外。追加写 JSONL 只是写入方式，防篡改还要靠存储权限、删除权限与保留策略。

按需要记录任务/作用域、节点、尝试或动作ID、事件时间、实际工具、脱敏参数或版本引用、执行状态与错误、审批与政策版本、检查结果及实际资源量。区分动作请求、批准、开始、完成、未知和接纳；请求事件只说明发起过，执行与失败各以对应事件为准。

事件可映射到任务开始、模型调用前后、工具请求/拒绝/执行结果、交接接纳、暂停/恢复、停止与结束。课程的 5+2 Turn 体系是一种映射示例；框架可能一轮多调用、最终回调才触发或异常被吞，需核对实际版本和路径。

关键测试验证「被拒绝时实际工具未执行」，以真实动作记录为准，异常、告警和界面文字只作辅助。策略初始化缺依赖时明确拒绝或报配置错误，在启动阶段就暴露问题。必要门控覆盖所有执行入口：框架吞异常、改用别的工具入口、子 Agent 和直接 SDK 调用都要经过同一门控。

已发生的资源先结算，再做终止判断；拒绝也留事件与原因。事件、账本与策略的顺序按依赖关系安排；远端 trace 阻塞要有时限，必需审计可在允许的可靠本地入口先保存。

日志默认只存必要字段，凭据不写入日志，只记脱敏标识或引用；完整提示词、全文、全部产物和内部思维链按需单独管理。必要正文用授权、脱敏、大小限制及证据引用管理；可选遥测可以采样，必需审批与安全审计全量保留，关键动作事实在发生时立即保存。质量监控、评测集和长期告警策略留下一章，Langfuse、OTel 和实时看板按需选用。

## 10. 最小示例与交付检查

以下仅为设计推演与契约样例，外部动作、鉴权、并发、恢复和模型效果都未实测；参数只用于演示。

### 示例一：生成答复草稿，经批准外发

单 Agent 或固定工作流：读取已授权问题 → 生成草稿 → 检查正文与接收者 → 必要人工批准 → 宿主执行发送并核对结果。本例只需这些节点，Manager、长期记忆和动态模型路由都用不上。演示最多 3 次模型尝试、工具总尝试最多 5 次、单次等待 20 秒、主动执行总时限 120 秒；人工批准有效期 1 小时，等待另计，资源预算继续累计。

宿主将任务、发送人、接收者、正文v1和一次性批准绑定，决定由有资格者通过受控入口登记。正文改成v2、目标改变、批准过期或被拒绝时都停止发送；服务授权失败时同样停止，批准只是额外门槛。

发送请求超时，且没有可靠的去重或结果查询时，停止重复发送，并把发送结果记为未知。沿用通用交接定义返回：

```json
{
  "task_id": "reply-1",
  "agent": "reply-worker",
  "status": "BLOCKED",
  "summary": "发送结果未知，已停止重复发送",
  "result": {"action_id": "send-1", "action_state": "UNKNOWN", "draft_version": "v1"},
  "blockers": ["需核对发送记录，当前无可靠查询或去重保障"],
  "unresolved_questions": ["接收者是否已经收到答复"]
}
```

任务和动作ID由可信记录提供；`result`是本例的业务字段，通用状态枚举保持不变。草稿生成成功只代表草稿完成，发送状态以核对结果为准；旧批准已用于本动作，恢复时先核对它，并沿用原发送动作的去重身份。

### 示例二：只读调查的有限重试与续作

单个只读调查节点按既有明确任务执行，演示最多 4 次模型尝试、工具总尝试最多 5 次、单查询最多 2 次追加重试、每次等待 10 秒、主动总时限 90 秒；全部修正与必要汇总共用额度。429按服务等待提示重试，等待都在剩余期限内；403直接阻塞，保持原身份。

因等待人补充关键来源而暂停时，保存目标、已核实结论与证据版本、缺口、已用模型/工具额度和恢复节点。恢复时先检查权限、来源版本和剩余额度；已完成的查询直接沿用结果，证据过期则按预算重新核实。来源处于合法等待中时，相同查询可能返回不变结果，需要结合进度判断，单靠输出哈希会误判为死循环。

必需来源仍不可读时，按部分完成或阻塞返回；允许部分交付时用 `PARTIAL` 并列出 `remaining`。本例无副作用，事务回滚、补偿服务、审批邮箱和多模型回退都用不上。

### 交付检查

把人工触发、负责人、实际材料、决定绑定、期限和恢复写第 8 节；错误、动作语义、重试、预算、状态恢复、安全执行与事件写第 9 节；具体工具规则留第 5 节，循环与委派边界沿用前章。

- 检查已读与批准分开、批准与授权分开，参数或版本变更后重新取得决定，停止入口独立于模型。
- 检查错误事实与动作状态真实，结果未知先核对，重试、修正和回退有共同上限与结束出口。
- 检查恢复沿用已完成副作用的结果和累计预算，回滚、补偿与取消如实记录不可逆动作已经发生。
- 检查资源调用前预留、调用后结算；固定模型可达标，粗估明确标为估算。
- 检查身份、数据范围、凭据、执行隔离与审计由可信层保证，必需保障失效时默认阻止，真实拒绝路径有验证计划。

反模式：每步都问人；自报高置信度免审批；已读或反馈即批准；ASK只告警；批准绕过DENY；超时即未执行；新幂等键重做旧动作；同输出哈希必然死循环；多层重试相乘；重启额度归零；回滚已发消息；换便宜模型绕过隐私；粗估事后查账称硬封顶；服务账号共享全部数据；正则保证无注入；沙箱环境变量即密钥隐藏；追加日志即不可篡改；安全组件异常时放行；只打印拒绝但工具仍执行。

依据：《企业级多智能体设计方法论精粹》第 27、30-33 课，Anthropic《Building Effective Agents》，旧设计建议 Skill 的异常处理、人机协同、资源感知、安全模式及旧协调模板。审批绑定、动作结果未知、幂等/恢复/取消、资源预留、身份与日志边界为本 Skill 工程归纳；素材中的攻击比例、价格、固定阈值和项目运行效果未经核验，本章只取其设计原则。
