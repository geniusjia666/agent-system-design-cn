## 1. 区分上下文、任务状态、长期记忆与知识来源

上下文工程（Context Engineering）是在每次模型调用前，选择最小但足够的高信号信息集合。上下文腐化（Context Rot）指长上下文中的信息召回或使用精度可能下降；窗口能放下的内容，模型未必都能可靠使用。

| 信息层 | 用途 | 常见混淆 |
|---|---|---|
| 当前上下文 | 本次调用的指令、用户请求、必要历史、工具定义和结果 | 应用中的全部数据；所有信息都必须常驻 |
| 会话与任务状态（Session / State） | 当前目标、参数、进度、产物、待处理动作及剩余预算；可按需持久化 | 跨任务适用的稳定知识；以为保存了状态，动作就能恰好执行一次 |
| 长期记忆（Memory） | 跨会话复用已确认的偏好、决策、事实或经验 | 全部聊天记录；自动拥有最高优先级的指令 |
| 权威知识与证据 | 当前代码、业务数据、正式文档及可核对的操作记录 | 模型摘要；上次回答天然可信 |

长上下文扩展本次可见信息，持久化解决保存与恢复，检索解决按需取用，记忆治理解决何时写与如何纠正；四者各管一件事。常见的请求式 LLM 每次调用只看到本次输入，应用需要提供历史、状态或读取入口。

只需单次分类时，任务输入和必要示例即可；多轮澄清可只维护会话状态；长任务中断续作可只保存任务笔记。只有明确需要跨任务复用时，才设计长期记忆。检索正式知识库时，用户记忆按需另行保存。

## 2. 设计有效预算与启动加载

### 有效预算

记录所用模型与接口的实际限制，并为输出和下一步操作留余量。预算包含系统指令、当前请求、历史、工具定义、检索结果，以及图像等输入按接口计算的消耗，聊天正文只是其中一部分。

```text
本次输入预算 = min(接口允许的输入上限, 模型上下文上限 - 预留输出) - 安全余量
```

如果接口已分别给定输入与输出限制，按其实际计数规则分别处理；安全余量覆盖估算偏差和预期增长。优先用可用的 token 计数接口或对应 tokenizer，粗略字符估算只用于带余量的预警。

先满足必要指令、当前目标、硬约束和关键证据，再给可选历史与检索内容分配预算。剩余预算不足时减少无关输入、分段读取或选择长任务策略；连必要信息都容纳不下时缩小任务、换合适接口或返回受阻，约束完整保留。

软触发阈值依据任务轨迹、信息保留率、时延和成本确定，硬上限在调用前强制检查。不存在对所有模型通用的「40% 拐点」或最佳压缩比例；长上下文质量下降是一种风险，「每条信息平均分到 `1/N` 注意力」并非定律。收费和时延按真实服务规则验证，注意力计算量推不出「账单翻四倍」。

### 启动加载（Bootstrap）

| 先加载 | 按需加载或不加载 |
|---|---|
| 当前目标、验收标准及可信行为约束 | 全部历史对话、完整知识库和全部工具说明 |
| 必要任务状态、原始需求与依赖入口 | 无关项目状态、其他用户画像或无用人设故事 |
| 当前角色需要的规范、索引和少量代表性示例 | 所有边界示例、所有记忆正文 |

用清晰章节区分指令、用户请求和参考数据。身份、用户画像、工作规则、记忆索引是可选的信息类别，可以放在任意载体中；有个性化或记忆需求时才加载对应内容。

导航包含主题、用途、可信来源、必要版本或时间，以及真实可读入口。索引也消耗预算，要限制当前相关项；文件、Skill 或主题数量增加时，启动成本也随之增加。

## 3. 在生命周期中按需组装信息

| 时机 | 做什么 | 必要边界 |
|---|---|---|
| 开始或恢复任务 | 加载目标、硬约束、当前请求及必要状态 | 校验会话、任务和访问范围，区分旧记录与新指令 |
| 每次模型调用前 | 选择当前相关信息、去重、检查预算，必要时剪枝或压缩 | 当前请求优先于旧摘要；保持消息协议完整 |
| 工具或检索返回后 | 检查真实状态、相关性、大小、来源和继续读取入口 | 分清空结果、失败、截断及结果未知；结果格式详见工具章节 |
| 里程碑或中断前 | 保存必要进度、证据、未决事项与剩余预算 | 只记录实际完成的事项；外部动作与保存状态分属两个事务 |
| 任务结束或记忆写入时 | 判断是否有跨任务复用价值，按准入规则更新 | 普通交付无需记忆 Agent；写入失败时如实报告 |

按需加载（Just-in-time Context）是持有轻量引用，任务需要时再读取正文；它与盲目探索不同，也可以和预先检索并用。稳定资料可预取以降低时延，动态代码与页面宜按当前状态读取；二者可组合。

来源涉及当前代码、文件、配置或实时业务状态时，以实际读取为准，旧笔记只作入口。索引未列出、默认检索没返回或摘要未提及，只说明还没找到；发现缺口后在授权与预算内换词、查相关入口，仍无证据则说明不足。

## 4. 选择剪枝、压缩、笔记或子 Agent

| 策略 | 何时优先使用 | 保留与代价 |
|---|---|---|
| 剪枝（Pruning） | 重复、已失效或用完的工具正文占用空间 | 保留关键事实和回读入口，以及仍需精确核对的依据 |
| 压缩（Compaction） | 大量来回沟通，早期历史需保持连续性 | 提炼目标、约束、决策、未决事项与来源；有信息损失和摘要调用成本 |
| 结构化笔记（Structured Note-taking） | 迭代开发、清晰里程碑、跨上下文或重启续作 | 外部保存进度及依赖，后续读取；需要同步真实状态 |
| 子 Agent 独立上下文 | 独立研究或分析需要大量探索，可通过有限产物交接，且简单做法不足 | 主 Agent 保留计划，子 Agent 返回结论、证据与缺口；增加调用、汇总及协调成本 |

默认先去除冗余，再按任务选择压缩或笔记；隔离有明确收益时才拆 Agent。三类长任务策略可以组合，按需选用；上下文变长只说明要管理上下文，多 Agent 另行判断。

剪枝前抽取仍有用的 ID、数值、来源、版本和动作状态，保留可回读引用。仍用于验收的证据按用途保留，与消息年龄无关；重复报错可以合并，影响后续选择的失败尝试与原因要保留。

优先使用客户端支持的上下文管理机制。自行处理历史时，按实际接口保护工具调用、对应结果及其他关联块；可整体清除已完成调用组，或采用接口允许的结果占位。调用与结果成对处理；按用户轮次切分是否安全，需按具体框架核对。

子 Agent 的输入须含任务目标、必要原始材料、约束、权限与预算；返回应含结论、来源、产物引用和未决问题，摘要只是其中一部分。独立上下文只隔离信息，权限隔离另行设计；完整的派发、共享状态及通信设计见多 Agent 章节。

## 5. 安全压缩与恢复任务

### 压缩最小流程

1. 选出可压缩的已完成历史段；保留当前请求、未完成调用和必须原样保留的约束。
2. 需要精确回溯的证据和记录先保存到已授权的可读位置；保存失败时保留唯一副本，并标明压缩有损。
3. 生成结构化摘要，先检查关键内容召回，再去掉冗余；摘要模型和后台服务按需另设。
4. 检查摘要保留了原有的目标、权限、数值、版本、动作状态与未决事项，按消息协议组装新上下文。
5. 替换前复核原状态未变化；预算检查通过后再继续。失败时保留可用状态，受预算约束重试、降级或返回受阻。

| 摘要或进度笔记字段 | 写什么 |
|---|---|
| 目标与约束 | 当前任务、成功标准、用户已确认的边界；旧目标单独标为历史 |
| 事实与决策 | 已确认结论、依据及必要时间或版本；区分观察、用户声明和待验证判断 |
| 进度与产物 | 实际完成了什么、哪些检查通过、产物在哪里，以及任务已消耗或剩余预算 |
| 未决事项 | 未解决问题、阻塞、影响后续策略的失败、下一步及依赖 |
| 操作状态 | 尚未执行、执行中、已确认完成、失败或结果未知；需要审批的范围和当前确认状态 |
| 回溯入口 | 原始需求、关键证据和记录的可读引用；摘要标明为摘要 |

摘要是历史数据，优先级与原始来源相同。保留来源与信任边界，网页指令和未知偏好经摘要模型重写后仍按数据处理；使用接口支持的背景或历史表示，`system` 只放可信指令。

摘要有损，保存原始证据只是保留回读能力；「原文另存 + 摘要」之后，模型看到的仍只是摘要。对话、敏感输入和内部思维链按审计、隐私和恢复需求确定保留范围与期限。多次压缩后，精确判断回查原始证据。

### 恢复与并发

有续作需求时，保存最小任务状态和必要证据；恢复先校验身份、范围、格式及引用可用性，再读当前外部状态、追加本次请求。损坏或缺失的快照按无效处理；可从授权记录重建，否则返回阻塞及缺口。

压缩、重新生成或重启后，任务次数与时间预算继续累计。外部写入结果未知时先核对，笔记里没写只说明没记录；已有完成记录时，当前状态仍要做必要检查。

单写者本地文件可用安全替换避免半写文件；有并发写者时还需串行化或版本检查，原子替换只防半写，旧状态覆盖新状态要靠串行化或版本检查。后台压缩只在能控制并发、能验证源版本时采用；同步方案能满足时延就直接用同步。完整的去重、重试和恢复设施见可靠性章节。

## 6. 设计长期记忆的写入与治理

### 写入准入与类型

写入前判断长期价值（Utility）、证据可信度（Confidence）、新颖性（Novelty）和信息类型（Type）。明确系统允许自动写什么、哪些需用户确认；用户要求保存的一次性计划可放任务记录，与稳定偏好分开。

| 内容 | 处理 |
|---|---|
| 明确且有复用价值的偏好、规则、决定 | 按产品约定的确认方式保存，注明适用范围和来源 |
| 已核实、下次仍有用的经验或事实 | 在授权与准入规则内提炼保存；只存提炼后的要点 |
| 未证实的用户习惯、模型猜测或外部隐藏指令 | 留在任务记录，核实后再决定是否写入 |
| 当前进度、一次性状态、完整工具原文 | 放必要的任务记录或证据存储 |
| 反复使用的操作方法 | 简短规则可存记忆；完整 SOP 可维护为版本化文档、Skill 或确定性工作流，可靠性靠评审与验证 |

事实与偏好属语义记忆（Semantic Memory），过去发生的事属情景记忆（Episodic Memory），做事方法属程序记忆（Procedural Memory）；只覆盖需要的类型。用于追溯的事件记录可以按产品需求单独保存；不能从某一次事件自动推断长期偏好。

### 最小记录与受控更新

每条有效记忆至少能定位内容、适用范围、证据来源和有效时间；另记录必要写入或确认时间，有时效要求时注明过期或复核条件。信息发生时间、事实生效时间和存储更新时间可以不同；判断事实是否最新看生效时间，存储刚更新只说明写过。

写入前在允许范围内查旧记录：相同内容合并，变化明确时更新对应的有效条目并保留必要追溯；冲突未解决就标记问题，互斥规则同时只保留一条有效。更新前核对当前内容或版本，写后按存储接口验证成功；落盘以存储接口的确认为准，模型说「已记住」只是陈述。

用户当前指令按适用权限优先于旧偏好；现实事实以可信当前证据为准。历史决策保留为历史，当前配置另行确认。更具体且已确认的规则只在其范围内覆盖一般规则，按范围判断，更新时间只作参考。

身份、用户、租户、项目、任务或共享范围由可信系统约束，按实际需要设计；检索、读正文、写入和输出均检查权限，范围由可信系统决定。文件目录隔离或数据库过滤是实现选择，读和写都要限制权限。

### 治理与存储选择

少量记忆可用受控文件、索引加主题正文或现有数据库；需要精确查询时加字段或全文检索，确有语义召回缺口时再加向量。内容规模、检索质量、写并发及维护成本共同决定是否升级，「几百条必须换数据库」只是经验说法。

按预算预警、引用失效、事实变化或产品约定周期触发治理，检查重复、冲突、时效、来源、死链及权限。有自动运行设施时才算已调度，Skill 描述里写的「每月一次」只是计划。

旧条目和低频内容都可能仍然有效；先判断类型和适用性。按用户授权与保留规则更新、停用、归档或删除；破坏性的批量清理需另获授权。删除或权限收紧同步影响索引和后续读取，归档也要限制访问；有隐私删除要求时内容要真正删除，挪进仍可搜索的归档不够。

写规范可由 Skill 承载，执行边界由宿主或服务强制；记忆写入用现有设施即可，三个 Skill、独立子 Agent 和 MCP 服务都按需引入。新建或修改可执行 SOP 需单独评审、验证和授权，能力扩展走这条路径，与记忆写入分开。

## 7. 按任务选择检索方式及证据规则

检索增强生成（Retrieval-Augmented Generation，RAG）是先取外部相关信息再支持生成；向量数据库只是实现之一，幻觉也只能减少。已给定且规模可读的材料直接读取即可；当前上下文充分时直接回答。

| 方式 | 适用信号 | 常见误解 |
|---|---|---|
| 按引用读取、文件检索或 `grep` | 已知文件、对象、错误码、函数名等精确定位 | 普通搜索一定比语义检索差 |
| 字段过滤与全文检索 | 时间、作者、对象、标签或文本匹配重要；可用现有数据库或搜索服务 | 全文排名天然满足全部业务约束 |
| 向量检索（Embedding） | 同义表达或概念查询存在实测召回缺口 | 相似就是正确、最新或被授权；能自动理解「上次」的时间范围 |
| 混合检索（Hybrid Retrieval） | 精确词与语义均重要，单一方法不足 | 所有任务必须混合；两套不同得分直接按固定权重相加就合理 |
| 关系查询或知识图谱 | 确实需要追踪已建模的依赖或关系 | 找到关系就证明结论，简单问题也必须建图谱 |

混合检索需要验证融合或重排方法与质量；权重、阈值、返回条数、分块大小和重叠按样例调优，课程中的数字不作通用默认值。可复用支持向量和字段过滤的现有服务，数据库选型按需求定，独立向量服务能否过滤元数据按其真实能力判断。

### 最小检索链路

1. 确认问题、权威来源及授权范围；明确时间和对象限制，先用合适的查询方式定位。
2. 读取有限候选；需要分块时按语义完整单元保留标题、来源、版本与上下文，太大或太碎都需检查。
3. 核对候选是否支撑问题，必要时读取原文、相邻段落、表头或前后依赖；结论以完整上下文为依据，匹配片段只是线索。
4. 对过期、冲突或缺失信息做判断，输出具体引用及证据边界；引用是否真的支持结论要逐条核对。

建索引时区分事实来源与模型生成摘要；一问一答未必覆盖多轮依赖，助手的猜测经确认后才能作为知识入库。需要向量时保证建库与查询使用兼容的模型和预处理，变更后明确重建或迁移范围。

原数据、摘要与索引的更新和删除应一致可追溯；稳定 ID 与受控更新避免重复且能反映修订；只用「重复时跳过插入」会让旧版本一直得不到更新。后台索引有延迟，近期内容未入库时按授权回查源记录；后台任务失败要能被发现，现有设施能做到时无需新队列。

### 空结果、历史指代与查询扩展

查询为空或一次无结果，只说明这次没找到。预算内可换别名、关键词、读取入口或检索模式；如果时间或标签只是系统默认假设，可明确扩大。用户指定的时间、业务条件和权限过滤保持不变；必要变更先澄清，扩大范围后的结果要标明条件已扩大。

「上次」「之前」需要任务对象和时间证据，语义相似度只是辅助。区分问发生过什么、问当前规则和问事实；分别查事件记录、有效记忆和权威来源。仍不足时标明缺口或受阻，查询次数有上限，没找到的历史如实说没找到。

## 8. 为 Agent 准备可读的信息环境

准备一份轻量地图，标明当前规范、需求、代码、设计决策、执行计划、证据与验证入口及各自的负责人或更新来源。已在仓库内的材料可版本化，外部正式文档只要有受控可读入口，也可以留在原处。

地图与正文分开，名称、目录、对象 ID 和时间是导航线索，结论以正文为准。死链、无权读取、旧版本与暂时不可用应能区分；正式来源不可读时暴露缺口，模型记忆只作线索。

访问并核对与当前任务相关的章节、代码及测试，按需加载；共享规范维护单一有效来源，各节点按需引用。改动同步必要的说明和索引；仓库改造、自动文档平台和完整的 Harness 实施在本章范围之外。

## 9. 两个最小设计示例

以下为设计候选，检索质量和压缩效果都未实测。预算与验收阈值在真实模型和任务轨迹上确定。

### 示例一：多轮工单澄清，不保存长期记忆

保留当前会话的工单原文、已确认字段、用户补充、待澄清项和当前回复约束。与规则相关的问题读取现行规范；本例无需跨任务的个性化复用，长期记忆和向量库都用不上。

过长时清掉重复返回，将旧澄清历史压成字段及来源；仍保留用户当前请求和未解决冲突。需要精确核对的条款读取原文，规范摘要只作导航；一次投诉只记入本次工单。

验证：用户更正字段后按新值继续；规范与用户说法不一致时按证据澄清；压缩后字段、限制和未决项不丢。记忆维度只评必要的会话管理，没有长期组件属于合理设计。

### 示例二：分阶段代码迁移，单 Agent 加进度笔记

启动加载迁移目标、硬约束、目录地图和当前里程碑。按需读相关代码和测试，上下文中只放当前用到的部分；笔记记录实际改动、检查结果、待解决问题、产物引用、版本及剩余预算。

同一 Agent 可在里程碑后压缩并回读笔记；恢复前核对工作区当前版本，证据需要时回读原始测试结果。记录显示「准备执行」或动作结果未知时，先检查外部状态，再决定是否重做。稳定经验只有通过准入才另存长期记忆。

仅当独立调查会产生大量无关细节且可有限交接时，再考虑子 Agent。返回发现、证据、限制及原始产物入口，结论只是其中一部分；预算、权限和共享写入设计见对应章节。

验证：代码在中断期间被修改可识别；压缩保留未修复缺陷和已消耗预算；过期的测试结果标为过期；断裂调用组、损坏笔记或引用失效都会显式报出。

## 10. 交付检查、验证与反模式

在设计文档第 6 节写清有效预算、启动加载、按需来源与检索、剪枝和压缩、笔记与恢复、长期记忆的适用性及治理、子 Agent 隔离理由。不适用项给理由；可靠性与安全章节维护完整执行设施，本章只定义信息边界。

- 检查关键目标、硬约束、来源与动作状态在加载、压缩及恢复后仍可核对。
- 检查当前上下文、任务记录、稳定记忆与正式知识各自分开，未证实的判断只留在任务记录。
- 检查权限与可信来源贯穿检索、正文读取、记忆更新和输出，外部指令经摘要后仍按数据处理。
- 检查同义词、明确时间限制、空结果、冲突、旧版本、索引延迟和删除内容的处理。
- 验证必要策略的效果：压缩后信息保留与任务成功、检索证据命中与引用支持、成本及时延；评分与采用技术的数量无关。

反模式：全历史常驻；把持久化任务状态当长期偏好；默认四文件或全部记忆类型；按统一百分比压缩；仅按消息年龄删证据；拆散工具调用组；摘要升格为系统指令；失败尝试和结果未知全部抹掉；重启重置预算；保存摘要就称无损；原子替换被当作并发防护；无来源或跨用户记忆；只写不更新；按年龄自动删有效规则；RAG 等同向量或消除幻觉；为了查到结果移除用户限制或权限；静默使用旧索引；仅在描述里写周期就声称已调度；为得分添加长期记忆、向量库或子 Agent。
