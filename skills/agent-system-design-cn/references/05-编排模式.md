# 编排模式

在主流程第 4 步选择执行结构，或评审流程中依赖丢失、错误传播、错误并行及循环失控时使用。本章设计节点和边，编排引擎的运行在范围之外；完整的角色、派发与共享状态见多 Agent 章节。

## 1. 先选择主模式，再判断是否需要组合

先问一次调用是否能满足标准；能满足就直接使用。否则先识别已知步骤、类别、依赖及真正需要模型决定的部分，再选最简单的主模式。

| 模式 | 适用信号 | 先排除什么 | 必须写清的控制点 |
|---|---|---|---|
| 提示链（Prompt Chaining） | 可预先拆成清晰、可检查的顺序子任务 | 一次调用已足够；步骤只是反复转述 | 上下游输入、必要更早产物、中间关卡及失败去向 |
| 路由（Routing） | 不同类别确实需要不同处理，且分类可可靠完成 | 所有路径实质相同；规则即可却另加分类模型 | 允许类别、选择方式、多意图与未知处理、兜底 |
| 并行化（Parallelization） | 独立任务可并发，或多候选比较有收益 | 未满足数据依赖；共享写入冲突；额外调用无收益 | 并发上限、聚合条件、任务身份、分支失败及超时 |
| 编排者-工作者（Orchestrator-workers） | 子任务内容或数量随输入变化，需要动态拆分、委派和汇总 | 固定拆分或单 Agent 执行足够；仅因文件多就拆 Agent | 计划校验、派发范围、依赖、扇出预算及汇总验收 |
| 评估-优化（Evaluator-optimizer） | 标准明确，评审能给可执行反馈，迭代有可测价值 | 单次生成加检查足够；只能给笼统自评 | 评审输入与标准、版本对应、修改范围、迭代上限 |
| 自主 Agent 循环（Autonomous Agent） | 下一步取决于环境反馈，固定路径难以覆盖 | 预定义分支或有界循环即可 | 真实观察、允许动作、宿主校验、完成与停止条件 |

前五类是常见工作流模式，第六类开放更多动作决策。工作流可以用模型分类、生成动态任务列表或判断质量，但允许的控制结构仍由代码限定；包含一次模型决策的流程仍属于工作流。

模式、控制方式与 Agent 数量分别判断。一个固定多角色流水线仍是工作流；并行工具调用可以留在单 Agent 内；工作者可以是受限 LLM 节点，自主循环按需配置。编排者-工作者的关键是动态子任务，角色、工具和权限可以预先定义。

只为明确缺口加辅助模式，通常先实现一个主模式。评估收益及成本后再组合，评分与模式数量、框架功能和组织角色数量无关。

## 2. 定义节点、数据依赖和校验边界

为每个节点注明职责、输入、产物和完成检查；普通数据转换与可执行检查优先由代码完成，LLM 调用只用在需要语言能力的节点。

| 边界 | 最小设计 |
|---|---|
| 数据依赖 | 上游、下游、传递字段及必要原始目标、更早产物；引用需真实可读，并能确认版本 |
| 控制条件 | 什么结果允许继续，什么情况修正、回退、降级、暂停或终止 |
| 校验关卡（Gate） | 必填与格式、业务条件、产物可用性分别怎么检查；谁执行、失败定位到哪个节点 |
| 资源与失败 | 节点修正或重试上限、外部等待超时，以及跨全部分支与嵌套循环的任务总预算 |

顺序边只保证先后执行，依赖数据需要显式传递；共享状态中有键时，正文也要显式放进下游输入。关键控制字段用类型、枚举及必填约束；给人的正文可以是 Markdown，JSON 用于需要机器解析的部分。

缺失、过期、不可读或未通过所需检查的输入，先处理再送下游，并留下记录。区分步骤已完成与产物被接受：评审任务成功返回 `FAIL` 时，执行状态可以是 `SUCCESS`，产物仍按 `FAIL` 处理。沿用现有交接的状态和评审结论。

修正格式、修复内容、瞬态重试和重新执行是四种不同的动作，按错误类型及剩余预算选择；上游变更后，只重新判断受影响下游的有效性，其余部分沿用。涉及写入且结果未知时先核对；完整的恢复设施见可靠性章节。

每条回边写终止出口。次数或时间至少一个由宿主强制，外部等待另设超时；局部上限都计入任务总额。沿用单 Agent 章节的一次尝试调用模型计一轮，含最终生成、评审、规划、修正；多节点及并行子任务也累计，框架口径不同须注明映射。

## 3. 提示链

将已知任务拆成固定顺序，每个 LLM 步骤处理上游产物。适合先提取再生成、先大纲再正文等任务，目标是用额外时延换取更容易检查的处理步骤，质量是否提高需要验证。

1. 按有业务意义的产物分解步骤，写每步的输入、输出与必要规范，每个节点对应一个可检查的产物。
2. 把原始目标、硬约束及必要更早产物显式传给下游，上一节点的摘要只作补充。
3. 在影响后续正确性的交接设置关卡，检查通过再继续；模型评审只加在确有需要的步骤。
4. 校验失败指向责任节点，带具体错误在预算内修正；超限或不可修正时结束或升级，回跳次数有上限。

阶段可以使用不同提示词、同一个模型或代码节点，专家人设和独立 Agent 按需引入。审核意见是对原文的补充，重构同时需要原代码与意见。

反模式：拆出很多只转述的节点；固定链被包装成自主规划；只传最后一句话；只检查格式就宣称事实正确；后续步骤机械执行已失效的输入。

## 4. 路由

按输入类别或当前状态选择合适处理器。优先使用现有可靠规则、传统分类器或模型方式，单一方法足够时直接使用，向量或多模型路由按需引入。

1. 定义允许的类别、各自真正不同的职责与统一输出；单选、多选或顺序处理多意图要明确。
2. 用有代表性的输入检验分类与兜底；模型返回先按允许枚举校验，执行入口只从允许集合中选取。
3. 为模糊、多意图、未知、非法输出或分类服务失败定义澄清、限定降级或人工路径；拿不准时走这些路径，最相近的类别只作参考。
4. 处理器执行前仍检查权限与审批；被路由到退款等流程之后，执行该业务动作仍需另行获准。

低置信度阈值需按实际分类方式验证；模型自报的置信分数需校准后才能当概率用。路由逻辑与处理职责可以分别检查，独立服务、多层路由和动态注册按需引入。

反模式：所有类别做同样的事；多意图请求只处理一半且不说明；未知类别默认为高风险动作；根据相似度绕过权限；为得高分组合多个分类方法。

## 5. 并行化

区分分片（Sectioning）与投票（Voting）：前者执行不同独立任务，后者对同一任务生成多个候选再按规则比较。并发适合 I/O 等等待；实际是否同时计算由执行资源决定。

并发前确认当前输入已就绪，分支之间无未满足的数据依赖，也不会争写同一未隔离资源。共享接口或规范先确定；有依赖的保持顺序。一个模型给出多条工具请求时，是否可并行仍按依赖判断。

| 聚合问题 | 规则 |
|---|---|
| 等哪些分支 | 默认等全部必需项；允许部分成功、首个有效结果或法定数量时显式定义条件 |
| 谁产生什么 | 结果携带稳定任务身份、状态、产物和必要版本；按身份及业务顺序组装，到达顺序只是偶然顺序 |
| 分支失败或超时 | 记录缺口，按约定重试、降级或阻塞；关键分支未通过时按部分完成或阻塞报告 |
| 提前结束 | 定义剩余任务如何取消或收尾，迟到结果是否接纳；取消请求发出后，外部动作是否停止仍需核对 |
| 并发资源 | 限制同时运行数与总扇出，预留汇总及验收预算；线程数按并发上限设定 |

投票写清可比较的输出、有效票数、平票或分歧处理。多次调用可能相关且共同出错，多数意见只是参考；安全筛查完成后才发送结果，业务分支先完成也要等筛查。

并行时延受关键路径、限流、排队及聚合影响，需要实际测量，最慢分支的耗时只是下限。比较端到端结果与串行基线，可控的小任务直接串行执行。

反模式：有依赖也并行；固定分支冒充动态委派；并发无上限；异常对象混入正常结果；到一个结果就声称全部完成；共享追加列表自动保证业务顺序。

## 6. 编排者-工作者

编排者根据当前输入动态产生子任务，受控派发，再综合结果。适合实际调查后才能确定材料范围或工作项的情况；预先知道的独立分支用普通并行即可。

1. 先取得足以拆分的事实；编排者需要读取能力时，为它配置相应的工具。
2. 计划写子任务目标、身份、依赖、必要材料、产物与验收条件。宿主检查引用存在、ID 唯一、依赖可执行、无误构依赖环及范围合规。
3. 对动态任务数、并发数、嵌套深度及总预算设硬边界；工作者能力从可信允许集合中选取，权限只由可信系统授予。
4. 只派发依赖就绪的工作，跟踪返回与缺失项；工作者返回结论、证据、缺口及可读产物，路径和完成通知只是其中一部分。
5. 汇总前检查覆盖计划、冲突及关键依赖；汇总可用确定性拼装，确需综合推理时再用模型，并验证最终目标。

动态计划可以配预定义的执行者，角色按需实例化。主节点只读调度是一种可选的职责配置；独立上下文只隔离信息，权限仍由宿主保证。

工单很多、文件多或报告长都只是线索。计划错误可能沿全链传播，派发前校验事实和约束；必要的独立评审按风险加入，规划评审 Agent 按需设置。

反模式：认为编排者替代所有固定工作流；只在 SOP 写边界却不执行；照搬「主 Agent 只读但自己写架构文件」的冲突示例；路径存在就认为工作合格；无穷扩张子任务。

## 7. 评估-优化与反思

先生成候选，再用明确标准评估并反馈修正。反思（Reflection）可以包含自检，验收以检查结果为准；任务内修正只影响本次任务，长期改进另需设计。

代码检查和真实测试能判断的直接使用；主观评价按准则使用单独评审调用或人工。生产和评审职责分开；不同模型、永久 Reviewer Agent 和证据可见范围都按需设定，另开上下文只能减少部分共同偏差。

评审拿到原始需求、约束、对应版本候选和必要事实或测试结果，以证据为准，生成者的自我辩护只作参考。最小反馈包含受检产物或版本、结论、具体位置、问题、修复建议与未决事项；沿用现有 `verdict` 字段，必要时给业务反馈定义结构。

| 结果 | 后续 |
|---|---|
| 必需检查通过 | 交付被检查的同一版本，改写后需重新检查 |
| 明确可修复问题 | 带反馈修改责任范围，再评估修改后的版本，次数及总预算有余量才执行 |
| 评审无效、标准冲突或缺少事实 | 在预算内纠正格式、补证据或升级；评审服务失败按评审无效处理 |
| 停滞、超限或无可行修复 | 返回最后实际验证的结果、可用部分与缺口，如实标为未达标 |

每次修改可能引入新问题，保留版本与检查对应关系；旧候选的分数只对应旧候选。`CONDITIONAL_PASS` 需写明条件与接纳者，条件满足前按未完全通过处理。预留最终检查预算；最后一次修正后的新结果完成检查后，才能作为已验收产物返回。

无需反馈修正的任务记此模式不适用。只有明确增益才反复迭代，迭代轮数在实际试验中确定，「直到完美」和统一三轮都只是说法。

反模式：把单次生成直接交付一概判错；模型夸自己就通过；同一次调用同时生成和证明正确；拿旧评分返回新版；重复修复无新证据；无限评审循环。

## 8. 自主 Agent 循环

由模型基于真实观察选择下一动作，宿主控制可用能力、参数、权限和预算。用于固定路径不足的开放式问题；能用已知分支处理的异常，直接用分支处理。

本章只写循环入口、允许动作、环境反馈与退出边界，内部执行顺序沿用单 Agent 章节：请求动作之后要真实执行，工具成功之后要检查任务，模型结束输出之后要验收。

每次决策保留原始目标、硬约束、当前状态和必要证据。遇到缺少输入、重复失败、无新信息或必要审批未获准，按规则澄清、暂停或结束；缺证据时去读取材料。

固定骨架可以只在一个调查节点嵌入自主循环，入口给有限范围，出口检查产物后才回主流程；其余流程保持固定，循环与费用上限由宿主强制。

反模式：固定工具序列称自主循环；模型不再请求工具就记成功；把审批拒绝当成可重试错误；结束时为生成漂亮总结透支预算。安全、超时和恢复设施详见后续可靠性章节。

## 9. 按需加入规划或探索

规划（Planning）是将目标转为可执行任务与依赖的能力，按需加入。预定义流程足够时直接使用；简单的自主查询直接执行，独立 Planner 按需引入。

把计划制定、校验与执行分为逻辑阶段，可以由同一个 Agent 承担。执行只取当前有效计划中的就绪项；新证据使假设、依赖或路线失效时才重规划，一般失败按错误处理。

重规划明确修改了什么、原因、已完成项是否仍有效及新增代价，再由宿主核对范围和依赖。依赖图发生变化后重新计算可执行顺序，旧的遍历列表随之作废，`plan` 变量与顺序一起更新。原目标、审批和总预算保持累计；变化涉及用户目标或权限时先确认。

探索与发现（Exploration and Discovery）用于确实存在未知、需要假设和验证的任务，普通事实检索直接检索即可。记录假设、支撑与反证、验证方法和当前结论；先验证有价值的假设，在授权范围与预算内考虑替代解释，模型的新观点经验证后才算发现。

探索结束条件是证据达到约定目标，或范围、预算、信息增益等既定停止条件触发。未证实的假设明确保留不确定性；多 Agent、知识图谱、复杂搜索算法和持续自我修改都按需引入。长期学习、自动实验平台与知识维护在本章范围之外。

反模式：每个步骤都重规划；新计划自动抹掉完成记录；有拓扑排序就称动态规划；未知就是无限搜索；置信分数等同实验验证；为了评分建图谱或探索小队。

## 10. 最小示例、交付检查与反模式

以下是设计候选，效果、性能与成本都未实测。两例预算只用于演示计数。

### 示例一：工单分类后走不同处理路径

主模式为路由工作流：输入 → 分类及枚举检查 → 常见问题答复草稿、退款人工审核或技术调查 → 各自检查 → 统一返回。未知或多意图未明确时先澄清；路由到退款只进入人工审核，退款本身由人执行。技术调查必要时可嵌入只读自主节点，其余路径保持固定。

原始工单与必要规则连同类别一起传给所选节点。演示配置为任务最多 4 次模型尝试，分类、生成、纠正与自主分支共用，单次模型或工具等待均有超时；超限返回缺口，未通过检查的草稿不得对外发送。

验证：正常分类到对应处理器，未知和非法分类走兜底；多意图全部保留或明确澄清；审批前没有副作用；节点切换后预算继续累计。此例无需多层分类、投票、Planner 或长期记忆。

### 示例二：生成代码 → 审查 → 必要修复 → 测试

主模式为提示链，确需修正时组合评估-优化。无问题且测试通过就直接交付。可用一个模型处理多个受限节点，已有隔离理由时也可用多个 Agent；顺序保持固定，仍是工作流。

审查读原始需求与代码，修复读代码、意见及相关测试。修改产生新版本，旧版本的通过记录只对应旧版本；最后交付实际检查的同一版本。静态检查与可独立执行的测试可并行，但测试依赖已写出的代码；全部必需检查完成后才能汇总成功。

演示配置为总计最多 6 次模型尝试、最多 1 次修复、外部等待有超时；生成、评审、修复与必要最终生成都计入总额，代码测试受时间与资源限制，不占模型轮次。若最后修复后没有预算做必需的模型评审，只交付可用部分及未验证说明，按未完整通过报告。

验证：无重大问题时原样交付；必需原始代码缺失则阻塞；修复新版要重新检查；顺序和版本按身份对应，与结果到达次序无关；超限、测试失败及评审结果无效都能明确返回。

### 交付检查

在设计文档第 3 节写主模式、辅助模式及各自收益，注明控制方式；第 4 节定义节点或 Agent，第 7 节写循环和数据交接，第 9 节维护统一预算与失败策略。不适用的模式说明理由，沿用现有模板。

- 检查所有必需输入有可读来源，依赖存在且可执行；固定无环片段不含误构环，有意循环有停止出口。
- 检查路由允许集合、未知与多意图兜底、处理器授权，以及动态计划和扇出硬边界。
- 检查并发的依赖都已满足、没有写冲突，聚合识别任务及版本，关键分支缺失时按部分完成报告。
- 检查评审反馈与产物版本对应，必要最终检查仍有预算，未验收的修改按未通过处理。
- 检查全部重试、修正、重规划及嵌套循环都计入适用总预算；实际收益用任务成功、时延和成本与简单基线比较。

通用反模式：为了角色或模式齐全而拆分；同一关键数据多次转述；路径顺序代替数据契约；Schema 合法代替业务通过；固定分支与动态子任务混同；编排者被当作唯一正确架构；把独立上下文当权限隔离；只传文件路径却不验产物；投票充当事实证明；无限回边；层层独立预算导致总额失控；迭代末返回未经评估的新产物。
