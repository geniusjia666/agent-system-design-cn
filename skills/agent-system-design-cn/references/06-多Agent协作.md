# 多 Agent 协作

在主流程第 4 步需要多个 Agent，或评审角色重叠、交接丢信息、共享写入冲突与任务悬空时使用。先沿用架构选型与编排结论；本章补角色、派发、状态和接纳边界，模式清单见编排章，数字员工平台超出本章范围。

## 1. 判断谁需要独立存在

职责不同是拆分线索，拆分还需要具体理由。每个新增 Agent 写明哪项确需隔离，为什么一个 Agent 的按需加载、分阶段提示或受限工具调用不够用，以及新增的时延、成本和交接风险。

| 隔离维度 | 需要回答 | 先考虑的简单替代 |
|---|---|---|
| 上下文与数据 | 独立调查会产生大量无关轨迹，或领域材料、任务状态、必要工作准则不宜混入同一上下文吗 | 按需加载、剪枝、笔记、独立任务节点；长期记忆按需引入 |
| 工具与执行能力 | 工具、SOP 或环境显著不同，混用导致选错能力、污染状态或执行不稳定吗 | 阶段限定工具、复用 Skill、受限函数；仅新增工具时先用这些办法 |
| 权限与信任边界 | 读写、业务授权或敏感数据范围必须分开吗；审查者需要保持源产物只读吗 | 宿主限制作用域和执行身份；必要的安全边界单独保留，即使另外两维相同 |

有一个实际隔离需求就可以支持拆分，但仍需与简单候选比较，维度数量本身不计分。决策偏好只在形成必要工作准则时考虑；研发、QA 等岗位名称只作参考，QA 与安全是否合并按实际隔离需求决定。

角色模板、任务节点与实例分别计数。一个实现 Agent 可连续做设计、编码、修复；多个研究实例可共用角色模板，各持不同的任务上下文。固定多角色流水线仍是工作流，角色多少不改变控制方式。能合并时减少角色，需要隔离时保留角色。

反模式：按文件数或组织架构拆分；要求三个或两个维度不同才准拆分；每个 Agent 必配人格和长期记忆；只改角色名却全量共享历史与工具；多 Agent 默认比单 Agent 可靠。

## 2. 定义职责与最小权限

为每个角色写职责宪章（Role Charter）：负责什么、不负责什么、产物与检查标准、争议交给谁。每项工作有确定的负责人和接纳者；同一角色可以承担多个兼容任务，负责人只对分配范围拥有写权限。

| 角色候选 | 典型职责 | 按需权限与输出 |
|---|---|---|
| 协调者 | 维护目标与有效计划、派发、核对覆盖与汇总 | 读必要任务状态与产物，写允许的计划和接纳记录；业务写权限另行授予 |
| 研究或调查者 | 在限定来源中核对问题与依赖 | 只读检索及必要查询，返回结论、证据和缺口；必要的只读命令可以使用 |
| 实现者 | 按已接受的需求或意见生成、修改产物 | 写明确分配的范围，记录产物版本、改动和实际检查；只改分配范围内的功能 |
| 审查或验证者 | 按需求与证据检查对应版本 | 对源产物只读；可写自己的报告，必要测试在允许的环境运行，测试本身也可能有副作用 |

这些是职责候选，按需选用。协调者只读业务产物是一种可选配置；需要取证、输出综合报告或直接处理小任务时，在契约中写明范围。协调与复杂执行混在一起导致上下文失控时再分开，主 Agent 可以执行契约允许的必要动作。

禁止事项（NEVER）帮助模型理解边界，实际执行由权限系统负责。可信身份、工具允许清单、读写范围和审批由宿主或服务强制；模型填写的角色名、`scope` 或能力卡只是声明，权限来自可信授权。共享工具可复用同一实现，每次调用都绑定正确的用户、项目、角色和作用域，身份由调用上下文传入，避免依赖全局可变配置。

先验证单角色的输入、返回与越界拒绝，再验证交接；执行隔离要单独验证，提示词测试通过只说明模型理解正确。上下文隔离、目录分开、不同实例与安全沙箱分别设计，各自解决不同的问题。

## 3. 选择协调结构与委派边界

固定顺序用代码协调，已有独立分支用受控并行；需要动态分工时，中心协调通常便于维护全局目标和任务清单，但可能成为瓶颈，也只是候选之一。协调者可以是宿主流程，Manager LLM 按需引入。

默认集中派发和接纳，执行者向协调点返回。只有收益明确时才增加角色间直连、发布订阅或多层协调，并写清允许的发送者、接收者、消息用途及修改任务的权限。QA 提出修复只是建议，研发范围由负责人决定；转派属于委派，同样受授权和任务预算约束。

下游只拿到显式组装的必要信息；即使框架共享会话，也按需组装。默认子 Agent 不再委派；确需嵌套时注明允许的角色、目标、最大深度、扇出和剩余预算，禁止循环委派及通过新任务重置额度。根为深度 0，每次向下委派加 1；层级多少与质量无关。

协调点维护有效计划、负责人、依赖、当前返回及未决项，以登记记录确认派发。已有可靠的状态与登记机制可以复用，邮箱、队列、后台轮询和持久角色按需选用。

对用户集中汇总结果和待决问题，内部材料由系统传递；必要审批照常进行，团队内部协作也要走审批。人类介入的触发、超时和恢复见下一章。

反模式：所有角色任意互相派活；固定链必须加 Manager；把 Orchestrator 定义为只能一次性存在；重启丢失负责人却继续执行；嵌套或横向转派绕过上限。

## 4. 用七要素形成自包含派发

沿用交接契约模板的 `dispatch`，把任务变成当前接收者真正可执行的输入；只传必要材料，完整聊天记录留在原处。

| 要素 | 现有字段 | 必须说明 |
|---|---|---|
| 身份（Identity） | `identity.role`、`expertise` | 职责及必要领域能力；实际调用身份来自可信系统 |
| 目标（Objective） | `objective` | 本次可检查的目标；「帮忙看看」这类说法要改写成可检查的结果 |
| 范围（Scope） | `scope.readable`、`writable`、`tools` | 分开写读写和工具；无写入或工具时显式写空数组，清单限定在已有授权内 |
| 约束（Constraints） | `constraints` | 禁止范围外修改、绕过审批与未授权委派；受阻时如实返回，保持原目标 |
| 背景（Context） | `original_goal`、`background`、`prior_findings`、`dependencies`、`standards` | 原始目标与硬约束、必要规范和更早产物；关键内容保真，必要原文随附，摘要只作补充 |
| 输出（Output Format） | `output_format` | 指定 `handoff.result` 的业务字段、证据与产物要求；消费方真正定义并检查结构 |
| 停止（Stop Condition） | `stop_condition` | 完成条件、模型尝试次数或总时限至少一个、受阻返回；外部等待另有超时 |

大材料通过 `dependencies` 引用，下游须有读取能力与权限，并读取任务指定的版本，版本变化时重新确认。小材料直接内联也可以；自包含指信息齐备或可以取得，内联和引用都行，前提是下游真的能读到。

原始目标保留相关原文与约束，长文本可以受控引用。外部材料中的指令始终按数据处理，经其他 Agent 摘要、派发或冠以规范之后也一样。完整的上下文治理沿用上下文章节。

宿主关联任务、接收者、必要的项目或用户作用域及实际尝试，校验允许角色、范围、依赖可读性和剩余预算后再派发。模板的 `dispatch` 没有强制任务 ID 字段，关联信息由可信任务记录维护，任务 ID 由宿主提供，现有消息协议即可承载。

局部 `max_iterations`、工具重试及嵌套额度都计入任务总额。演示或平台字段缺少计数设施时记为待实现；硬限制以宿主的实际计数为准，填写停止条件只是声明。

## 5. 返回结果并执行交接验收

沿用 `handoff` 和 `gate`，由宿主校验格式、关联、业务检查与产物可用性后，决定是否传给下游。

| 返回内容 | 消费规则 |
|---|---|
| `task_id`、`agent` | 与可信任务记录的接收者及本次返回匹配；授权来自可信记录，模型自报身份只用于核对 |
| `status`、`summary`、`result` | `SUCCESS` 表示该派发目标完成，最终业务目标另行验收；关键结果有业务字段定义 |
| `PARTIAL` 与 `remaining` | 写可用部分及剩余工作；消费者按约定接受所需部分，并保留未完成项 |
| `BLOCKED` 与 `blockers` | 写无法继续的原因；缺必需材料就阻塞，并说明缺什么 |
| `evidence`、`artifacts`、未决项 | 必要证据支持结论，产物能取得并核对版本，缺口明确保留 |
| `verdict` | 验证任务成功执行可返回 `FAIL`；`CONDITIONAL_PASS` 的条件由明确接纳者判断 |
| `metrics`、`confidence` | 供诊断或参考；预算以宿主实际记录为准，验收以检查结果为准 |

交接模板是定义库，校验时引用对应的 `$defs`，根对象没有约束，不承担校验。通用 `result` 允许任意对象，完整性要靠具体业务字段定义；需要防串版的业务把 `artifact_ref.version` 等可选字段改为必填并由宿主检查，通用 Schema 只保证结构。

`gate.required_fields` 与 `business_rules` 是待执行的规则，由宿主真正执行。格式和可执行条件由代码检查，必要的主观评价可单独评审或交人工；宿主读取实际判定再决定路由，业务规则由生成者以外的检查方执行。

先确认产物与返回可用，再登记接纳并传下游。位置存在只说明能找到，正文是否正确另行检查；工具成功只说明调用完成，文件是否按预期修改另行核对。上游换版后，重新判断下游产物和检查是否有效；缺必要依赖时责任节点暂停，汇总如实保留关键失败。

校验失败沿现有 `on_fail` 的当前步修正、退回责任上游、升级或降级处理；`max_retries` 与任务总预算共同约束，超限返回已有结果、原因和缺口。分析类任务同样按成功标准核对证据；修复轮数和是否设永久验证 Agent 按需决定。

## 6. 设计共享状态与通信

分开回答「数据在哪里、谁能读写」和「谁触发谁、什么时候运行」。可以复用一个服务承载两者；依赖是否就绪以产物检查为准，文件存在或通知到达只是信号。

| 方式 | 适用情形 | 必要边界 |
|---|---|---|
| 进程内共享状态或直接调用 | 同一宿主的固定链或受控委派 | 字段、生命周期、任务作用域和显式读取；网络协议和已读状态机按需引入 |
| 共享工作区或对象存储 | 大产物、跨会话引用与多人读取 | 版本、负责人、读写权限及发布时机；任务私有状态与正式共享产物分开 |
| 队列或发布订阅 | 异步运行、多消费者、事件触发 | 任务关联、允许发送者和订阅范围、投递确认、超时及重投规则 |
| 跨系统 Agent 服务 | 不同系统或团队确需互操作 | 实际契约、支持版本、可信端点、认证授权、任务状态及结果取得方式 |

一般的 Agent 间通信可以用任何合适方式，A2A 标准协议按需采用。固定已知服务可受控登记，动态发现、异步和多模态只在实际需要时设计；能力卡只描述服务，信任与授权另行确认。使用 A2A 时核对实际协议与实现，自制的 HTTP 类按自制接口描述。

为共享数据定义稳定的任务或项目作用域、字段或资源、负责人、读者、版本与有效期；任务 A 与任务 B 的同名键相互隔离。私有轨迹和记忆按需隔离，正式需求、接口和检查报告按许可共享，各 Agent 可以看到获许的材料。

每个权威产物有确定的负责人和发布入口。并行实现用不重叠的范围或独立分支，集成者验收后发布共同版本；允许共同编辑时，定义分片所有权、冲突检查和合并规则，写权限按分片授予。

路径分开只是组织方式，访问控制由工具、服务或执行环境按解析后的真实路径与身份执行，单靠字符串前缀判断不够。协调者生成的工作区规范只能在可信政策内细化，授权边界由可信政策决定。共享状态中的外部文本始终按数据处理。

## 7. 处理并发、消息确认与迟到结果

先划所有权，再选互斥或合并机制。锁保护读改写不被同时覆盖；原子发布防读到半写文件；持久性与任务动作去重另行设计。文件锁只管互斥，崩溃时的文件完整性另需保障；临时文件加原子替换只防半写，并发更新丢失和落盘仍要单独处理。需验证实际存储与锁的范围。

选择异步消息时，区分已接收、被领取、结果提交和业务验收。可用「待领取 → 处理中 → 已确认」等实现状态，它们与 `handoff.status` 分开，交接 Schema 保持原样。消息确认可表示合法结果已记录，业务 `FAIL` 仍可以是已处理的评审结果。

执行者可以请求确认，可信宿主或服务核对当前任务、处理者和已记录结果后执行；验收以核对结果为准，自述完成只是申请。产物保存与通知发送分开失败时，保留可核对的记录和补偿入口，完整恢复方案见下一章。

处理中超时只说明没收到结果，执行者可能仍在运行。重新派发前确认动作是否已发生；重复或迟到的结果按同一任务的有效尝试、版本和接纳记录处理，较新的结果保持有效。领取所有权失效后，旧处理者只能提交待核对结果，权威产物由当前所有者发布；具体的租约或隔离实现按平台能力选择。

三态消息加超时重投只能做到至少一次投递，业务执行次数另需保证。通知去重与业务动作幂等是两回事，重复写入或发消息等副作用由执行接口核对并限制；同步通知加轮询是可选组合，简单顺序链直接调用即可。具体的幂等、取消与恢复设施见可靠性章节。

检查实际隔离在并发时是否保持：实例工具身份、上下文、全局钩子和缓存可能串用。某框架需要全局锁属于该实现的问题，团队是否串行按自身需要决定；有证据的兼容性限制在落地映射中注明。

## 8. 按需设计优先级调度

优先级排序（Prioritization）只在资源竞争、截止期或重要性冲突影响任务时增加；固定依赖或先来先服务（FIFO）足够时直接使用，模型打分、动态重排和复杂队列按需引入。

先过滤授权、输入、依赖、资源与预算不满足的任务，再在就绪集合中按明确规则选择。高优先级同样要等依赖就绪、审批通过；选中任务前由宿主统一检查并预留并发与预算额度，避免各分支读取同一剩余预算后同时超额派发。

需要排序时，写清标准、平局规则和最大等待处理：紧急程度、业务价值、截止期、资源代价按实际需要使用，规则足够时直接用规则。新事件确实改变标准时才重排；设置最大等待防止低优先级无限饥饿，执行中任务的取消或抢占另有允许条件。

优先级决定就绪任务的先后，目标和权限保持不变；保留选择原因和任务身份即可，内部思维链无需公开。上限及全局计数沿用编排规则。

## 9. 用 SOP 固化协作及映射框架

标准操作规程（SOP）记录目标、必要阶段、参与职责、输入和产物、验收、分支条件、停止与升级规则，适合通过 Skill 按需复用。固定的可执行约束仍在宿主或服务中执行；SOP 指导模型选择允许的动作，可靠的固定边界保留在代码中，「零 Python 编排」只是口号。

SOP 变更时，核对角色、字段、依赖与检查是否仍兼容，按风险评审及回归；新增角色也要核对可信名册和权限，兼容性以核对结果为准。团队复盘与持续改进见评测章节，记忆、技能和代码的修改按需经评审进行。

框架只映射同一交接设计：ADK 顺序执行配合 `output_key` 存状态，下游显式读取必要键；LangGraph 用 State 和条件边；CrewAI 用任务输出与必要 `context`；AutoGen 用类型消息和主题订阅。这些机制只负责承载，原始目标传递、版本校验和业务验收仍由宿主设计，具体版本与骨架代码见框架章节。

## 10. 最小示例、交付检查与反模式

以下是设计候选与契约示例，模型、调度和业务效果都未实测；演示上限仅用于说明。

### 示例一：生成 → 审查 → 必要修复

固定工作流，示例因生成与审查上下文分离、源代码写权限分离而使用多个受限 Agent；代码实现者可承担修复，两种角色就够，额外的 Manager 也用不上。宿主掌管顺序、共享版本与接纳。

派发给实现者的修复契约示例（状态键为逻辑位置，由宿主提供读取与写入映射）：

```json
{
  "identity": {"role": "代码实现者", "expertise": "Python"},
  "objective": "只修复审查指出的问题；没有必要修改时原样返回代码",
  "scope": {
    "readable": ["state.generated_code", "state.review_comments"],
    "writable": ["state.refactored_code"],
    "tools": []
  },
  "constraints": ["不得改变需求范围", "不得再委派", "必需输入缺失时返回BLOCKED"],
  "context": {
    "original_goal": "实现单词计数函数，正确处理空字符串与标点",
    "dependencies": [
      {"name": "generated_code", "location": "state.generated_code", "version": "code-v1"},
      {"name": "review_comments", "location": "state.review_comments", "version": "review-v1"}
    ],
    "standards": "审查结果必须说明受检版本；修复后重新检查"
  },
  "output_format": "handoff.result = {refactored_code: string, applied_comments: string[]}",
  "stop_condition": {"success": "返回完整代码及意见处理结果", "max_iterations": 1, "on_blocked": "写明缺失材料"}
}
```

宿主先读取并核对两份依赖，审查的业务结果须带 `reviewed_version = code-v1`；只有意见、缺原代码时就阻塞。示例中宿主内联已核对的材料并保存返回产物，因此不调用工具；需要自主读取时，在 `scope.tools` 中声明已有授权的读取工具。

演示预算为全任务最多 6 次模型尝试、最多 1 次修复，模型与外部检查各有超时；评审、修复与重新评审共享总额。没有问题时原样返回；新版本完成必需检查后，才能作为已通过交付。

### 示例二：受控并行只读调查

多个独立来源确需隔离详细轨迹，使用相同调查角色的不同实例或不同的受限工具配置；宿主负责协调，人格、长期记忆和动态服务发现都用不上。各派发保留同一原始问题，按来源分范围，返回结论、证据和缺口，协调者核对冲突与覆盖。

某必需来源不可读时，返回示例：

```json
{
  "task_id": "investigate-source-b",
  "agent": "investigator-b",
  "status": "BLOCKED",
  "summary": "必需来源当前不可取得",
  "result": {},
  "blockers": ["来源读取被拒绝，未核实该分支结论"],
  "unresolved_questions": ["该来源是否存在支持或反驳原问题的证据"]
}
```

任务 ID 和实际实例由宿主对应。演示为 2 个分支、并发上限 2、总计最多 5 次模型尝试、每分支最多 2 次，预留汇总所需的尝试，且每个外部等待都有超时；预算不够时跳过模型汇总。必需分支阻塞时，总体按部分完成或阻塞报告，允许部分结果时注明缺口；证据冲突如实列出，依据证据本身判断，多数票只作参考。

### 交付检查

设计文档第 4 节写角色与隔离理由，第 5 节写工具权限，第 7 节写交接、状态与委派，第 9 节统一预算与失败规则。无跨系统服务或资源竞争时，通信协议和优先级增强写不适用及理由。

- 检查角色、节点与实例数量明确，职责无悬空，每个新增 Agent 有实际隔离及成本理由。
- 检查派发七要素、原始目标和更早产物齐备或可读；任务、实例、作用域和版本由可信记录关联。
- 检查业务 `result` 与接纳规则确已定义，合法 JSON、收到消息或执行成功之外，还有对应的业务验收。
- 检查权威产物的负责人、并行写入范围、实例配置与发布入口明确，私有状态在任务之间隔离。
- 检查必要的失败、重复、迟到、超时和嵌套边界有允许去向，全部分支共享适用的总预算；具体实现未验证时如实标注。

通用反模式：按岗位堆角色；无隔离仍拆分；提示词或目录即权限；调度器必为模型；只传上一轮摘要；只给不可读路径；错版意见改新代码；任务与用户串用同名状态；多个 Agent 任意覆盖权威产物；三态消息声称恰好一次；标已读等于验收；高优先级跳过依赖；局部预算叠加超总额；嵌套或直连无限派活；固定链为评分引入 A2A、动态发现或复杂优先级；自述分派和完成替代实际记录。
