# 单 Agent 设计

在主流程第 3 步使用，也用于第 4 步的单 Agent 内部循环。先沿用架构选型结论，再定义任务单元；本章列出多种能力，每个节点按需选用。

## 目录

1. 按架构裁剪设计范围
2. 定义角色、目标与工作准则
3. 写出任务契约与验收规则
4. 按需设置里程碑与进度监控
5. 选择必要的推理方式
6. 设计真实反馈驱动的执行循环
7. 写清停止条件和返回方式
8. 定义工具与上下文接口
9. 两个设计示例
10. 交付检查、反模式与来源

## 1. 按架构裁剪设计范围

| 任务单元 | 本章必须写什么 | 按需才加的内容 |
|---|---|---|
| 单次模型调用 | 输入、输出形态、完成标准、失败返回；明确一次调用及有界超时 | 人设故事、工具循环、里程碑、长期记忆 |
| 固定工作流中的模型节点 | 节点契约、所需依赖、验收与失败去向；有重试时写上限 | 动态规划或自主 Agent 身份 |
| 自主单 Agent | 职责边界、契约、推理方式、真实反馈循环、停止条件、工具与上下文接口 | 为完整性配齐所有推理技术 |
| 多 Agent 中的一个成员 | 按其实际控制方式采用以上规则，再说明职责为何独立 | 把成员职责、整个团队编排和共享状态全部塞进本节点 |

任务（Task）描述本次要交付什么，角色描述这个任务单元负责什么，流程描述谁决定下一步。一个角色可以执行多个任务；多次模型调用可以由同一个 Agent 完成。

## 2. 定义角色、目标与工作准则

将角色（Role）、目标（Goal）、背景（Backstory）用作组织提示词的参考，各框架按需填写。背景优先写成工作准则，没有必要内容时写「不适用」，经历只写真实的。

| 项 | 怎么写 | 避免什么 |
|---|---|---|
| 角色 | 负责的领域、工作范围及交付对象，例如「只读故障调查员」 | 用「顶级专家」代替职责；认为角色名称能保证知识正确 |
| 通用目标 | 在多项允许行为间如何取舍，例如「优先核实证据，不以猜测补齐」 | 与本次任务目标、输出要求或权限限制冲突 |
| 工作准则 | 何时核实、何时澄清、如何处理不确定性及业务规范 | 冗长人设故事、无来源知识、互相矛盾的指令 |
| 能力边界 | 能读取什么、能产出或修改什么、不能做什么 | 只写「谨慎操作」；用提示词替代实际权限控制 |

区分通用目标与本次任务目标：前者是偏好，后者是具体交付要求。两者必须相容；发现冲突时先修正定义，硬约束由人来定。

固定业务步骤、审批、验收和权限限制可以且应明确规定。「给模型选择路径」只适用于已授权的自主部分，操作规范照样写清。某次任务专属、可能冲突的流程放进任务契约，复用角色只放通用内容。

## 3. 写出任务契约与验收规则

先填写现有设计文档的 Agent 定义表，沿用同一套模板。

| 契约项 | 必须说明 |
|---|---|
| 本次目标 | 要交付的成果、交付给谁、支持范围；终点写成具体结果，「深入分析」这类说法要改写 |
| 输入 | 用户原始目标及硬约束、材料来源与格式、必要依赖；缺哪些就无法开始 |
| 输出 | 消费者需要的字段或文档结构、字段含义、必要证据、产物存放位置 |
| 完成标准 | 何时算完成、由谁检查、检查失败后怎么办 |
| 停止条件 | 最大轮次或总时限至少一个，外部调用有超时；受阻和超限如何返回 |
| 禁止事项 | 越权读写、修改目标、编造事实或工具结果等具体禁令 |

输出结构按消费者选择：给人的报告可用 Markdown 章节，给系统的结果定义字段、类型和必填项。自然语言回复按需使用 JSON，单次任务只取多 Agent 交接契约中用得上的部分。

复杂产物可以保存后传引用，但要说明接收者如何读取；说「文件已生成」时，必须有可访问的产物。

### 把标准变成检查

| 检查类别 | 例子 | 判断机制 |
|---|---|---|
| 格式与结构 | 必填字段、枚举、长度、Markdown 必需章节 | 宿主代码、JSON Schema、Pydantic 或文档检查 |
| 业务与事实 | 分类是否属于允许集合、结论与引用是否相符、改动是否满足测试 | 业务规则、测试、来源核对；无法完全自动判断时用约定的模型评审或人工 |
| 交付可用性 | 文件存在且可读、输出能被下游解析 | 宿主或接收方实际读取验证 |

字段描述帮助模型理解质量要求，要求的执行另由检查完成。Schema 通过只代表声明的结构约束通过，事实正确、业务目标完成和系统操作成功另行检查。

对主观标准写清评价准则和评审者，模型自述「符合要求」只是线索，验收另由检查方完成。能用规则或测试检查的优先直接检查，简单任务无需评审 Agent。

## 4. 按需设置里程碑与进度监控

目标设定与监控用于长任务、多阶段交付或需要发现偏离的任务；简单任务只保留完成标准。

1. 把目标拆成可验收的产物，每个里程碑对应一个阶段性成果，「想一次、搜一次、点一次」这类微操作留在里程碑内部。
2. 为每个里程碑写输入、交付物和检查标准。通过检查后再标为完成。
3. 记录已完成、当前处理、剩余工作和阻塞原因；进度依据产物及检查结果，调用次数只用于预算。
4. 发现偏离时，可以调整搜索或处理策略，目标、验收标准和权限保持不变；确需改变时交给用户确认。

监控由现有宿主承担，角色、看板和评分器按需另建。运行记录只需支持当前任务的恢复、验收和后续排查，详细监控体系见评测章节。

## 5. 选择必要的推理方式

| 方式 | 何时用 | 设计边界 |
|---|---|---|
| 直接回答 | 输入充分、结果简单，单次处理即可候选达标 | 一次处理完成，无需循环 |
| 分步推理（思维链，Chain-of-Thought） | 已有材料上的多步分析、计算或约束推导 | 保留结论依据和必要计算，内部思维链无需公开 |
| 推理与行动交替（ReAct） | 需要外部证据，下一步取决于真实工具反馈 | 工具由宿主执行，结果来自真实返回 |
| 先规划后执行 | 多步任务有依赖，需要先明确里程碑 | 只有反馈使计划失效时调整；完整规划模式留到编排章节 |
| 多候选比较（思维树，Tree-of-Thought） | 有明确评价标准，比较多个方案可能有价值 | 写候选数量及预算；按评价标准和收益决定是否启用 |
| 有反馈的修正（自我纠正，Self-Correction） | 测试、校验或评审指出具体错误 | 带错误修正，限定次数；纠正效果需要验证 |

按任务需要选择，思维链、ReAct、思维树和自我纠正按需组合，得分与组合数量无关。需要确认事实时，读取真实材料。

可审计的是输入依据、工具请求与实际结果、关键决策摘要、产物及检查结果，内部推理过程无需留存。对外按需要解释结论，公开思维链不属于设计或验收要求。

中间存储只在保存产物、检查节点或恢复任务有实际价值时使用；保存工具只服务于这些业务需要。

## 6. 设计真实反馈驱动的执行循环

ReAct 的关键是「根据真实观察决定下一步」，文本标签只是一种实现。采用以下逻辑，与具体框架 API 无关：

1. 宿主读取任务契约，检查输入和权限，初始化进度及本次任务的计数或截止时间。
2. 每次调用模型或工具前检查取消、阻塞和资源上限；预算只由宿主调整。
3. 模型基于原始目标、必要材料和真实历史结果，提出工具请求、待确认问题或候选结果。
4. 工具请求先由宿主校验名称、参数和权限；需要审批的先暂停。校验或审批未通过时，不执行工具。
5. 宿主真实调用工具，并把成功、空结果、错误或超时如实写回。模型根据真实返回继续，计划中的调用在执行前只是计划。
6. 候选结果交给约定的检查机制；通过才记为完成；未通过时，把具体问题反馈给模型，是否再生成取决于剩余预算和错误类型。
7. 需要澄清或无法继续时暂停或结束，返回已有结果、缺口和下一步需要谁做什么。

工具调用（Tool Calling）或函数调用（Function Calling）的结构化请求可用于分离模型请求与真实执行。文本版 ReAct 的停止标记（Stop Token）只是某些实现的解析机制，按需使用，权限校验另由宿主完成。

「生成了工具请求」之后，还要看工具是否执行成功；「工具返回成功」之后，还要看任务是否通过验收。只有实际结果可以作为环境反馈；网页真正读过、测试真正运行过，才能说已验证。

## 7. 写清停止条件和返回方式

区分本次模型输出结束、任务成功、暂停和兜底终止。`Final Answer` 或停止标记只表示模型这次停止生成，任务是否完成另行检查。

| 触发条件 | 处理规则 |
|---|---|
| 用户取消、权限或必要审批被拒绝 | 停止新的操作并说明原因，限制保持有效 |
| 总时限或硬资源预算已耗尽 | 停止调用模型和工具，由宿主返回已有产物及终止原因，结论如实标为不完整 |
| 候选结果通过全部必需检查，且未触发以上硬停止 | 标记成功并直接返回，此时轮次恰好用完也照常结束 |
| 结果未达标，模型轮次已用完 | 结束，返回已完成部分和缺口；没有可用部分时说明阻塞 |
| 连续动作无新证据、重复失败或缺少关键输入 | 按事先定义的纠正、澄清或停止规则处理；本次任务上限继续累计 |
| 需要人工信息或确认 | 暂停并提交问题；写明等待超时和恢复方式，等待期间按未完成记录 |

轮次需要有明确口径。本 Skill 的示例按「一次尝试调用模型」计一轮，最终答案生成、格式修正和重新生成都计入同一任务总额；工具重试单独设上限，同样计入任务预算。框架计数口径不同的，在落地时注明映射。

最大轮次和总时限至少定义一个；有工具或其他外部等待时，还必须有有界超时。上限由宿主强制，提示词里的「最多尝试几次」只是说明。预算数值按任务和试验确定，课程中的 100 轮是演示值，不作默认。

需要结构化返回时，沿用现有约定：成功为 `SUCCESS`，有可用部分但未完成为 `PARTIAL`，无法继续为 `BLOCKED`。部分完成写 `remaining`，阻塞写 `blockers`；对人的回复可以用自然语言表达同样含义，字段按需输出。

单 Agent 本章只确定触发条件与去向。错误分类、退避重试、幂等与断点恢复的完整实现见可靠性章节，本章沿用那里的状态与恢复设计。

## 8. 定义工具与上下文接口

| 接口 | 本步写什么 | 后续再展开什么 |
|---|---|---|
| 工具 | 需要哪些能力、何时调用、允许的读写范围、审批及返回中的关键证据 | 工具描述、参数、防呆、MCP 或 Skill 接入 |
| 上下文 | 原始目标、硬约束、必要依赖、最新真实结果、当前进度 | 按需加载、剪枝、压缩、记忆治理 |
| 持久化 | 是否需要保存产物或进度、保存后谁读取；无需保存时写「无」 | 断点恢复、版本管理和共享状态机制 |

只保留与当前任务有关的信息，每个节点只拿到所需的历史和工具定义。记忆按需开启；跨任务复用必须有明确需求和治理规则。

## 9. 两个设计示例

以下为设计候选，预算是演示配置，未经性能实测，只用于说明。

### 示例一：已给材料的客服工单分类

| 项 | 设计 |
|---|---|
| 控制方式 | 单次模型调用，不建立自主循环 |
| 职责与输入 | 接收工单原文及已提供的分类定义，只判断类别，回复客户和修改工单在职责之外 |
| 输出结构 | `category` 为业务允许类别或「需人工判断」，`reason` 为简短分类依据 |
| 完成标准 | 必填字段齐全、类别合法；实际分类准确率在评测集中检验，格式通过只说明结构正确 |
| 推理、工具与记忆 | 直接分类或必要分步分析；无工具、无长期记忆、无需背景故事 |
| 停止与失败 | 演示配置：1 次模型调用、单次超时 10 秒；格式失败或超时交人工，调用总数保持 1 次 |

分类是否正确由评测集检验，无需模型自评；本例用不上反思、工具和进度监控，缺少它们也是合理的设计。

### 示例二：只读故障调查 Agent

| 项 | 设计 |
|---|---|
| 角色与通用目标 | 只读故障调查员；优先核实证据，无法确认时保留不确定性 |
| 本次目标 | 调查指定服务、环境、时间段的一条报错，输出已确认事实、候选原因和下一步验证动作；根因可能找到，也可能只留下候选 |
| 输入 | 报错原文、服务与环境标识、时间范围、只读资料入口和允许范围；缺服务或时间范围先澄清 |
| 输出结构 | `facts`、`hypotheses`、`next_checks`；事实关联真实来源，假设单独标记，阻塞或剩余工作按返回状态填写 |
| 完成标准 | 范围一致、必需字段齐全、事实与实际来源对应、假设与根因分开标注、下一步动作具体；既有规则能检查的由宿主检查，语义判断按约定评审 |
| 推理与循环 | ReAct；根据日志或文档的真实结果选择补充查询；只读调查，修改服务配置和修复都在权限之外 |
| 工具与上下文 | 只读日志、文档查询；保留原始目标、关键结果与剩余缺口，只用会话内状态 |
| 停止配置 | 演示配置：最多 6 次模型调用或 120 秒，先到者限制继续执行；外部请求最多等待 15 秒，且不得超过剩余总时限 |
| 无进展与阻塞 | 演示配置：连续 2 次查询无新增证据时检查原因，允许的替代查询也无法推进则结束；权限失败或必要材料不存在时直接返回阻塞 |

可能的执行轨迹：第 1 轮读取日志；第 2 轮因证据不足查询相关文档；第 3 轮提交带来源的报告并通过约定检查，结束。若第 6 轮后仍请求补查，宿主停止调用模型、第 7 轮不再启动，返回已有事实及剩余工作；没有可用结果则返回阻塞。

## 10. 交付检查、反模式与来源

把职责、输入输出、完成标准、推理方式和停止条件写入设计文档第 4 节；单 Agent 循环写入第 7 节；工具和上下文接口分别写入第 5、6 节。同一约束在各章节引用同一份定义，保持一致。

- 检查每个任务是否有具体交付物，是否把通用目标、任务终点及权限混写。
- 检查必需标准由谁验证，是否把结构通过、模型自评或停止标签当作业务成功。
- 检查模型调用、格式修正、工具等待和人工等待是否都受既定上限约束。
- 检查受阻与超限是否返回真实缺口，是否仍保留原始目标和必要证据。
- 检查选择的能力是否确有需求；固定节点按需配置循环，可审计以依据与结果为准，内部思维链无需公开。

反模式：空泛专家人设；Goal 与 Task 冲突；不给完成标准；Schema 通过就认定事实正确；模型伪造工具观察；看见 `Final Answer` 就标成功；用额外保存工具凑推理轮次；重试或重规划重置预算；为评分配齐全部推理模式。

依据：Anthropic《构建有效的智能体》（Building Effective Agents）、《企业级多智能体设计方法论精粹》第 02、07、08、09 课，以及旧设计建议 Skill 的「目标设定与监控」「推理技术」模式。停止优先级、计数口径、背景可省略及示例预算是本 Skill 的工程归纳，并非原文逐字结论或实测结果。
