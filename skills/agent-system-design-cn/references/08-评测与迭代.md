# 评测与迭代

在主流程第 1 步判断需求适用性、第 6 步设计评测，或评审系统的质量与迭代机制时读取。先有具体用例、可执行标准与基线，再补必要工具；实时看板、A/B 平台、自动学习和微调按需引入。

## 目录

1. 需求适用性：先验证价值与前提
2. 原型：用最小范围验证关键假设
3. 评测用例：分开定义、记录与结论
4. 评测执行：按系统边界准备环境
5. 评分：先确定对象，再选择评判者
6. 汇总：正确解释成功率与重复试验
7. 变更门禁：快反馈与可信发布
8. 线上监控：从业务目标反推信号
9. 数据回流、复盘与受控学习
10. 最小示例与交付检查

## 1. 需求适用性：先验证价值与前提

适用性回答值得解决什么问题，不替代架构选型。先确认使用者、触发场景、当前做法或未满足需求、实际频率与耗时、错误代价、负责人，以及业务增长时的瓶颈。结合现有文档、实际工作流和获准使用的数据核实；没有专职人工岗位的任务也可能有价值。

| 检查视角 | 写证据，按事实判断 |
|---|---|
| 规模效应 | 统计范围、频率、单次耗时、等待与重复工作；低频高价值任务及现成工具也可值得做 |
| 任务清晰度 | 输入、输出、业务标准、例外与不支持范围；能写规则的部分先检查普通代码是否足够 |
| 错误后果 | 影响对象、是否可检测/撤销、复核与纠错成本、必要审批；高收益不能抵消禁止动作 |
| 信息可用性 | 必要来源是否真实存在、可授权读取、质量与时效、整理和接入成本；结构化数据同样要核对正确性 |
| 实际价值与瓶颈 | 节省什么、增强什么、过去不能完成什么；怎样确认用户采用且业务改善 |

五维表是讨论框架，按证据逐项判断，课程中统一 25 分、18 分立项或每周 10 次的门槛不予采用。先解决数据、授权、验收等阻塞项，或缩小试点；缺信息标待确认，关键风险单独处理，其他维度得分再高也要先解决它。

比较人工、普通代码、现有服务与最简单模型候选。按同一业务范围、质量要求和周期估算收益、调用/工具费、部署维护、人工审核和错误处理成本，注明假设与范围；节省的时间按实际用途换算，与现金收益分开记录。价值可同时记录时间、质量和新增能力；「时间×质量÷成本」只是粗略比较，得不出可比的财务回报率。

结论选不需 AI、前提不足暂缓、限定试点或已有证据支持推进；AI 有价值时，是否需要自主 Agent 另按架构章节判断。具体控制方式和角色数量沿用架构章节的分档。

## 2. 原型：用最小范围验证关键假设

明确谁使用、何时需要输出、AI 提建议还是执行、成功的业务变化与底线。单轮/多轮、嵌入式辅助、事件工作流、UI 自动化或平台是产品形态，可以组合，Agent 数量另行判断；主动、上传或事件触发按实际流程选择，后台触发的价值同样要验证。

选一个最影响方向的未知假设，写支持/否定/证据不足分别怎么判断；其他假设列为未验证，单个假设通过只是上线前提之一。限定输入、知识和状态来源、输出消费者、不做项、预算与结束条件，用最简单可行候选跑代表性场景，并与当前做法比较。

先定义基准事实或参考标准（Ground Truth，GT），再做验收；GT 可为可核实事实、结构化目标、期望终态或带锚点的质量准则，唯一文本答案只是其中一种。标准与 I/O 相互校准、版本化；不得在看过候选后改动答案让它通过。

用户验收测试（User Acceptance Testing，UAT）验证真实输入、理解和工作流适配，离线正确性、安全与集成检查另行完成。受控原型可以先跑主流程，涉及真实数据或副作用时，从首次运行起就保留必要的权限和停止围栏；「先忽略异常」只适用于原型，上线前必须补齐。

原型发现至少包括假设及证据、基线与候选差异、标注或数据质量问题、实际用户行为、未验证范围和下一步。样本量与周期按变异、风险及可用资源决定，50/200/1000 条和 1 天/2 周只是参考量级。本 Skill 只设计验证方案，未实际执行的标为待验证。

## 3. 评测用例：分开定义、记录与结论

评测用例（Eval Case）是版本化静态场景；执行记录保存实际输出、工具事件、状态、耗时和费用；评分记录绑定用例、运行、评分器版本与证据；发布决定另按门禁形成。期望定义来自业务标准，一次实际失败或模型自报成功只记入执行记录。

| 用例字段 | 最小设计 |
|---|---|
| 标识与分类 | 稳定 ID、用例版本、功能/场景、来源、风险或优先级；难度按需，边界用例的优先级按风险定 |
| 输入与初态 | 用户请求、必要上下文、可信身份/作用域、知识版本、工具或环境夹具；多轮另写脚本或用户目标 |
| 评分标准 | 必须满足什么、禁止什么、检查方法及证据、必要硬失败项；参考答案可选 |
| 执行协议 | 被测边界、隔离/重置、轮次/时限/资源、允许重试；评测答案不得注入被测上下文 |
| 适用过程约束 | 必要动作、依赖、参数/对象范围和终态；存在多条合法路径时，只约束必要动作与终态 |

这些是评测业务字段，通用 dispatch/handoff/gate Schema 保持原样。数据量大时放在已有测试或数据集管理处；设计文档保留代表性用例和引用，新平台在确有需要时再建。

数据来源组合使用：已核验历史样本打底，专家覆盖高后果与未见边界，合成变体补缺口，线上记录揭示真实失败。历史输出、点赞或审批要先核验才能作 GT；合成题与答案须验证业务语义，换一个模型生成只是另一个候选，真实性另需证据。

用功能×场景矩阵覆盖主流程、歧义/缺输入、空/多结果、边界、权限、安全、服务失败及适用恢复。按风险增样，每格数量按需要定，每格恰好 1 条或至少 3 条只是示例；语义相近但揭示不同失败的案例要保留，相似度去重前先检查会不会删掉关键边界。

分开开发/调优集、回归守底集与未用于调优的留出评测集（Holdout Set）。训练、提示示例、检索材料和调参记录可能泄露答案；按来源、模板、任务/用户或时间分组划分，避免同源变体跨集。对留出集反复调参会使其变成开发集，需受控更新并保留旧基线。

新增、纠正、去重、失效或退役均形成新版本，记录理由、覆盖变化和负责人；保持历史结果可解释，集合可以增加、修改或退役。隐私最小化、脱敏、来源授权、保留/删除和访问范围沿用数据治理；用户会话按保留期限处理，作为学习资产需另获授权。

## 4. 评测执行：按系统边界准备环境

| 被测系统 | 执行与证据 |
|---|---|
| 单次调用 | 输入及必要前后处理真实执行，保留输出、格式检查、用量与失败；若含检索/工具也纳入边界 |
| 多轮对话 | 固定用户脚本便于定位指定路径；动态模拟按实际回复推进，写用户设定、隐藏目标、停止条件并校准模拟器；二者都只覆盖部分真实用户 |
| 固定工作流/多 Agent 链 | 检查必要节点输入、产物版本、交接、聚合及终态，含循环或条件时按实际图检查；同时测试缺产物和错误传播 |
| 自主 Agent | 在授权环境真实执行允许工具，记录关键决策摘要、动作和结果，检查目标、过程限制及真实终态；完成通知只是线索 |

模拟返回（Mock）、契约测试、受控真实服务分别证明不同范围。按变更影响选择：提示词也可能改变写入路径，改 Prompt 后同样按影响选择验证层级；模拟通过只覆盖接口形态，认证、服务语义、并发和真实副作用另需验证。

需要时为每个案例或试验设置独立作用域、已知初态、隔离的记忆/缓存/动作记录、可核对夹具和清理规则；无关初态保持可比，故意测试缓存或续作时明确状态承接。外部发送、支付等改用受控测试目标，重置只在隔离的测试资源上进行。

沙箱类型沿用安全章节，Docker 只是选项之一。工具错误、超时、审批拒绝、结果未知、预算耗尽、取消和迟到结果按适用风险注入；拒绝测试以实际动作未发生为准，警告只作辅助。

记录适用的代码、提示词、模型实际版本及参数、工具/Skill、知识/索引、环境夹具、用例集、执行器、评分器、策略与运行时间。服务无法锁快照时，记录可获得的标识、依赖与漂移风险，并如实标注版本不稳定；`temperature=0` 或固定 seed 只降低随机性，端到端确定性仍需验证。

每次试验保存实际尝试、失败和预算，最大轮次按已定义计数口径；重复试验与业务重试分开。工具、服务或评测执行器故障时，先记录真实状态并保留失败记录；已发生的副作用沿用原动作键核对。

## 5. 评分：先确定对象，再选择评判者

区分输出质量、任务完成、允许过程与资源约束。字段提取/分类可用精确规则；开放式生成用必要事实、覆盖、相关性和表达准则；动作任务核对实际对象/版本与终态。命令退出码为 0、HTTP 200、格式正确或有引用都不足以单独证明业务正确。

| 方法 | 适用与校验 |
|---|---|
| 代码断言 | Schema、允许值、事实/集合、产物可用性、终态、顺序依赖、权限及资源；自身用正例、反例、边界和缺数据验证 |
| 模型评判（LLM-as-a-Judge） | 难以规则化的语义/主观维度；提供原任务、必要事实、标准、锚点、候选及版本，返回结论、简短依据和缺证据项 |
| 人工评审 | 领域判断、真实用户价值、高风险验收、评分器校准或争议；可以作为主力评审方式 |

能用可靠代码判断的优先用代码；关键词出现、BLEU/ROUGE 相似或「不含 UUID」只证明所定义的窄规则，语义正确和敏感信息另需检查。前置硬失败可以跳过昂贵评分，未执行的检查保留「未执行」状态，各维度分别记录。

过程评测断言必须成立的不变量、偏序依赖、参数范围与禁止动作；仅在固定 SOP 确有要求时比对完整顺序。当前版本的「黄金轨迹」只是参考路线，其他合法路线同样有效；工具使用频率变化需结合结果判断是否退化。

模型评判隐藏候选来源，控制位置/长度/风格偏好；两两比较可交换顺序，结果冲突时记为不确定或复核，胜者由证据决定。自评与同系列模型有偏差风险，使用时须独立执行、校准并注明限制；多个不同 Judge 也可能共同失误。

用已核验人工样本覆盖好坏、边界和高后果类别，检查误判的混淆矩阵、失败检出率与误报率，按类别/风险选择阈值。除总体一致率还看类别不平衡；二元指标写正类定义、precision/recall 的分母。Judge、准则或数据分布变化后重新校准；不得用统一的 85% 一致率宣称可靠，可靠性按校准结果判断。

量表每档给可辨识锚点，两两对比定义更好/相同/更差和不确定。要求可审计的简短依据与证据，内部思维链无需提交；评分器生成的参考答案只是候选，权威事实仍来自原始标准。无证据、评分格式错误或服务失败记为评分无效，被测业务按未判定处理。

## 6. 汇总：正确解释成功率与重复试验

先固定计划案例、运行次数、检查与排除规则。分开实际业务通过/失败、未运行（NOT_RUN）、执行环境错误、评分无效及未决项；这些是评测记录状态，与通用交接枚举分开。

报告计划/已运行/可有效评分数量与覆盖、可评分运行通过率，以及对计划集的完成情况。未运行和无效检查单独计数，不计入通过；排除只能按事前协议进行并列出原因，难例和临时服务失败都保留在报告中。用户视角的端到端成功率按实际请求协议计入服务和恢复代价，离线有效样本率另行报告。

按功能、风险、难度、来源和必要用户/任务切片统计，同时保留总体与数量；质量、安全、成本等硬项单独判定，均分抵消不了。设计自检的 0-5 分只评文档与证据，线上成功率和发布授权另行判断。

| 指标 | 定义与使用 |
|---|---|
| 单次成功率 / pass@1 | 指定系统及运行协议下，一次运行达标的概率；用户一次请求可能包含协议内的有限恢复，需注明 |
| pass@k | 同一案例 k 次尝试中至少一次成功的概率；用于多候选或允许重复试验的能力评估，需说明如何识别/选择成功及额外成本 |
| pass^k | 同一案例 k 次运行全部成功的概率；衡量重复可靠性，与用户一次机会的成功率是不同指标，是否作为门禁按系统需要定 |

定义一次运行是否包含工具重试、模型修正或多候选选择；这些内部次数不计为 k 次独立机会。测试判分器挑出最好候选的 pass@k，只说明候选中有正确答案，产品能否自己选对另需验证；输出成功时，先前的不可逆错误动作仍计为失败。

仅在同一案例各次成功独立且同概率 p 时，`pass@k = 1-(1-p)^k`、`pass^k = p^k`。跨案例成功率不同时，先逐案例计算再按目标分布聚合，直接对整体平均率乘方会出错。相关故障、共享状态或自适应重试下用实际联合结果，独立公式在这些情况下不适用。

从每案例 n 次试验中随机取 k 次（n≥k，成功 c 次）的经验组合比例为 `1-C(n-c,k)/C(n,k)` 与 `C(c,k)/C(n,k)`，分别对应至少一次/全部成功，约定 a<k 时 C(a,k)=0。推广为未来概率需要合适的采样假设；n<k 时标证据不足，结果只作推演。连续运行和随机子集的协议不同要注明。

重复运行记录所有尝试与代价，预先设试验预算和判定方式，汇报全部结果。样本少、重复运行相关、用户/任务聚类或多版本频繁比较时说明不确定性；使用适当置信区间或按任务分组的重采样；一两次波动先复核，再判断是否退化。

新旧候选尽量在相同用例/环境/评分协议上配对比较，报告改善、持平、退步、未决及切片风险。固定已批准基线用于发现长期退化，也可同时对比当前线上版；更换数据或评分器时，重评可比版本或标明不可比。更新基线需经审核并留下版本和理由；基线只在审核后更新，过时后及时替换。

## 7. 变更门禁：快反馈与可信发布

持续集成（Continuous Integration，CI）验证变更；测试通过、代码合并、发布批准与部署成功是不同事实。复用共同检查，按影响选择必要套件，流水线数量按需要定；完整流程、阈值和负责人写入现有交付体系。

| 变更 | 验证重点 |
|---|---|
| 代码/运行器/配置 | 静态、单元与契约、关键端到端、错误/预算/权限执行路径 |
| 提示词 | 格式、语义/边界、实际行为、必要副作用及成本，字符串检查只是其中一项 |
| 模型/参数/服务版本 | 代表性质量、工具兼容、稳定性、安全、性能与成本，按影响扩大 |
| 知识/索引 | 来源、授权、时效、检索覆盖和引用支持，必要删除/更新同步 |
| Skill | 触发、加载、指令边界、工具与产物交接、上下文代价 |
| 工具/接口 | 参数、返回、认证授权、超时/结果未知、幂等与真实集成 |
| 用例/评分器/门禁策略 | 正反例、校准、覆盖和比较口径；准则改变带来的分数变化与系统改进分开报告 |

按风险、依赖和费用排序：廉价配置/Schema及关键授权检查先跑，小型守底回归尽早反馈，再跑适用行为、质量、集成、稳定性、性能与安全套件。关键安全检查按风险尽早执行，可以排在固定的「第五关」之前；必要项全部完成后，才形成相应的准入结论。

CI 可以异步启动并允许继续提交，但必需状态仍为待定时，不得自动合并或发布候选；检查绑定具体提交、配置、数据与评分器版本。新提交或关键输入变化后，重新判断适用结果，旧的通过报告只对应旧产物。外发和修改办公系统需要单独授权，自动执行本身不含这项授权。

硬失败阻断；证据不足、质量权衡或评分争议走受控审核；必需检查有效通过、阈值及审批满足才按已有权限准入。禁止动作无法由人工豁免，未运行也只能记为未运行；允许的风险接受应有范围、理由和有效期，历史结果保持原样。

运行/评分器故障、超时和flaky case有定位、有限重跑及负责人，失败与重跑结果并存。隔离不稳定用例时，保留覆盖缺口、替代保障和恢复条件，用例本身留在集合中。硬失败也包括关键业务、数据完整性和预算底线，一条失败即可阻断；模糊探针命中先核实，确认后才记为事故。

支持按允许范围受控试点、影子验证或灰度；影子任务不得重复真实发送或写入；A/B 分组考虑用户/任务关联、代表性和风险，随机试验按需采用。部署与回退绑定有效版本及兼容状态，配置回退只影响配置，已发生的外部副作用保持已发生。

报告注明变更、快照、基线/候选、各项数量与结果、未运行/无效/退步案例及证据、资源、覆盖缺口、门禁决定和负责人。优先复用现有测试、CI和日志；自托管工具同样要核查模型调用和遥测数据是否出域，平台API、探针数量和安装命令以核验过的文档为准。

## 8. 线上监控：从业务目标反推信号

评估与监控（Evaluation and Monitoring）分别回答样本上的表现与线上是否持续满足目标。观测与可靠性安全章节的执行围栏互相补充；HTTP 200 只说明请求成功，任务成功另需检查，基础服务故障也可能影响模型之外的行为。

| 视角 | 选择适用信号 |
|---|---|
| 业务 | 完成、采用、返工、处理周期与用户价值；代码提交数或点击量只是代理指标，提效要结合结果判断 |
| 质量 | 必需事实、输出可用性、端到端完成、真实反馈/抽查及评分器有效率 |
| 执行 | 各工具实际结果、节点/版本交接、必要检查、恢复、停滞、取消和结果未知 |
| 资源/系统 | 输入输出及实际计费项、调用/并发、缓存、端到端/必要首字延迟、依赖可用性 |
| 安全/合规 | 越权、泄露、危险动作与必需审计缺失等具体事件，按真实政策处置 |

每项写分子/分母、样本范围、窗口、切片、来源、目标/阈值、延迟及缺数据处理、负责人和响应。总体配合分工具、版本、任务与必要用户切片；工具失败、模型轮次、子 span 数和无结果比例分别计数。

周期报告、人工抽查或已有指标足够时直接使用，实时看板按需建设。异步抽样按风险/流量/成本选，保留采样概率与覆盖，高风险或罕见问题增样；富集的失败样本用于分析，总体失败率按原始采样估计。未完成任务、晚到反馈与脱落单独记录，统计范围覆盖全部用户。

确定性统计聚合与语义标注分开，模型评分定期校准。输出质量趋势看适用窗口与样本不确定性；重大单次风险立即响应，无需等平均率变坏。服务级目标（Service Level Objective，SLO）清楚时可用多窗口错误预算燃烧率，消耗率按其明确定义计算，各类通知保留各自的阈值与算法。

动作写暂停、升级、受控降级或回退及恢复条件，阈值按实际风险验证，不照搬固定 30 步、1% 抽样或一周只告警。停滞启发式可以在观察中校准，硬权限与总预算从首次执行起生效；切换到更便宜的模型，同样要满足隐私、质量和工具兼容要求。

线上重评或代码测试在授权的隔离环境执行，真实副作用用受控目标替代；测试、模型评判、代码运行和遥测都有成本。只保留必要的脱敏事件与证据，上传完整会话需单独授权，用户不满本身不构成授权。

## 9. 数据回流、复盘与受控学习

数据回流循环（Data Flywheel）是信号→核验/分类→代表性用例→根因与候选改动→离线验证/门禁→获准试点→线上确认，每一圈都要验证是否真有进步。少量人工整理和受控发布也能形成闭环，自动化程度和收集范围按需要定。

显式评价、纠正、审批与隐式采纳、修改、重问、中断可用于找案例，这些都只是信号：批准表示允许动作，0.85 这类质量分需另行评定；复制的内容可能有错，退出也可能是正常结束，拒绝工具可能是正常政策。没有反馈只是没有信号，隐式覆盖也有遗漏，达不到 100%；行为数据先经核验，再用于训练标签或成功率统计。

意图/纠偏/解决（Intent/Correction/Resolution，ICR）帮助发现哪类任务摩擦大；与真实结果、可见性、延迟和用户群体交叉核对。低召回启发式可以先找到部分值得分析的案例，重大风险仍需专门检测；信号采集需要授权、最小化和保留范围，禁止隐蔽监控个人设备。

将原始可核对事实、症状、根因假设、支持/反证和当前可信度分开。先看具体失败，再用开放编码（Open Coding）记问题、归类并验证可行动类别；根因可以是未知或多因，分类按实际情况定，四枚举只是参考。首个可见失败点未必是根因，评分器、服务与数据也可能有问题。

复盘五问作为数据检索指南，顺序可以调整，组织者按需指定，判断结合犯错者以外的证据：

1. 哪些任务或切片表现不足，依据、分母与严重程度是什么？
2. 偏差在哪个节点出现，输入、版本、动作与真实结果是什么？
3. 人类纠正或其他独立证据支持什么，又有哪些矛盾和缺口？
4. 根因有哪些候选，怎样区分并验证，而不是仅说「下次注意」？
5. 改什么受控对象，如何验证收益/回归风险、谁批准及如何回退？

按严重程度、受影响范围、频率、修复可信度与成本排序，分类条数只是因素之一；少量严重案例也可以立即调查。样本不足时只下局部结论，类别暂时饱和时也可能仍有未覆盖的风险，复盘有范围、预算和停止出口。

学习与适应（Learning and Adaptation）区分任务内纠正、合规个性化/记忆、跨任务提示词/工具/流程更新与模型权重训练。静态策略可经维护者离线改进，动态环境同样可以离线改进；无需持续适应的系统，学习组件记为不适用。

根因决定最小改动：资料/索引缺失就核实和修来源，参数契约错误就修工具，约束丢失修输入/交接，评分错误修评分器，能力缺口再比较模型或训练。「80% 都是 Harness 问题」只是经验说法，按实际根因判断；Prompt→RAG→微调阶梯可以按根因跳步。合成数据可以使用，真实分布验证仍要另做。

提案至少包含证据、根因假设、对象及当前版本、具体改动、预期验证、风险、负责人/审批与回退条件。读真实内容再定位，按接口选锚点或补丁；基线不匹配、锚点歧义或目标越权时拒绝并重读，字符串替换同样需要这些检查。

按实际影响、权限与政策分级，memory、soul、code 的风险都按实际内容判断，与文件名无关。模型可以提出候选，可信层控制写入、版本、测试、批准和生效；目标、权限、评分器和必需门禁不得由模型自行放宽。自动更新只在已授权范围及已验证的围栏内进行，人工批准和测试都要完成。

改动后在目标失败类、未用于调优的数据与其他关键类重验，保留正反效果及旧记录；没有改善证据时可以拒绝或停止。小改动分开便于归因，单条回退前须检查后续依赖，并说明可能影响的其他改动。定期合并重复/冲突规则、退役失效例，保留历史与隐私删除边界。

## 10. 最小示例与交付检查

以下是用例设计与数学推演，真实模型、服务、用户和发布效果都未实测。示例 ID 和业务字段只用于说明，相应的工具和评测运行器尚待建设。

### 示例一：工单分类与答复草稿

候选为固定路由工作流：限定类别，读取获准知识，输出类别及有依据的草稿；未知或缺关键材料时转人工，结果只留在内部。先与人工和单次调用比较，再验证路由与知识的实际收益，本例无需多 Agent 或微调。

| 用例 | 初态与输入 | 标准与实际验证计划 |
|---|---|---|
| FAQ-1 主流程 | 给定故障描述、类别定义及当前获准FAQ夹具 | 类别匹配；草稿必要事实受材料支持；未发送外部消息；规则+必要语义复核 |
| FAQ-2 边界 | 语义模糊且缺必要对象信息 | 最少必要澄清或按范围转人工；对象由用户确认，结论以材料为依据 |
| FAQ-3 失败 | 唯一必要知识源返回403 | 保持原身份与授权；如实报告阻塞与缺口，检索状态按实际返回；核对实际拒绝事件 |

单条静态定义可写：

```json
{
  "case_id": "FAQ-3",
  "case_version": "v1",
  "input": {"user_message": "请查询这个故障的处理办法", "scope": "test-user-a"},
  "setup": {"required_source": "faq-fixture-v1", "source_response": 403, "external_send_allowed": false},
  "grading_criteria": ["报告必要来源不可访问", "不绕过授权", "不声称已检索或已解决", "不发送外部消息"],
  "execution_protocol": {"max_model_attempts": 3, "max_tool_attempts": 3, "active_timeout_seconds": 60},
  "meta": {"feature": "工单答复", "scenario": "required_source_denied", "source": "expert_crafted", "risk": "high"}
}
```

次数和时限仅演示；被测系统读取夹具中的实际403响应，评分标准和预写答案只留在评分侧。用代码判断权限、动作和必要字段，主观内容经校准评审；执行证据缺失记为未决，三条草案齐全只说明用例设计完成。

### 示例二：代码生成→审查→修复的版本与稳定性

沿用固定三角色/节点交接，测试原始需求、代码版本与审查意见可读；修改v2后必须跑针对v2的真实检查，v1报告只对应v1。评测计划覆盖正常依赖、缺审查产物、测试失败、预算耗尽、迟到旧结果；编译和测试通过后，需求覆盖是否完整仍需另查。

冻结夹具、用例和评分协议做重复试验。数学示例：同一案例单次p=0.8且各次独立同分布，k=2时pass@2=0.96、pass^2=0.64；用户单次机会仍为0.8。若两个等权案例分别p=0和p=1，二次至少一次与全部成功的总体概率都为0.5，用平均p=0.5直接计算会错误地得到0.75和0.25。

某案例n=10次中成功c=6，随机取k=2次的经验组合比例为pass@2=13/15、pass^2=1/3；这是全部已记录试验的子集统计，与直接代入0.6得到的0.84/0.36不同，也只描述已记录的试验。n<k、共享状态或故障相关时按协议说明证据边界。

版本门禁示意：v2必需测试未运行→待定不准入；评分器异常→评分无效不准入；硬约束失败→阻断；有效检查通过且获准→仅准入对应v2；v3改动后重新判定，旧的通过报告只对应旧版本。对比时保存所有失败和资源，如实报告全部运行。

### 交付检查

适用性写设计文档第1节，假设及待确认写第11节；评测/监控/回流/变更准入写第10节。工具、恢复、安全与执行审计留前章，只在本章注明验证它们的方法。

- 检查用例、执行、评分与准入分开，至少有主流程、边界和失败草案，来源/版本/夹具/准则可核对。
- 检查必要真实结果与过程限制，Mock、UAT、语义Judge和真实集成各自证据范围明确，拒绝时实际动作未执行。
- 检查未运行、评分无效、真实失败、覆盖缺口与所有重跑保留，分母和采样明确，重复指标不混淆。
- 检查基线与版本可比，评分器有正反例及必要校准，旧检查只对应旧产物，硬失败单独判定。
- 检查线上信号有负责人、窗口与响应，反馈先核验再作GT，批准与质量分开，提案经授权和验证再生效，学习平台按需建设。

反模式：适用性分数替代前提与风险；低频一律不做；先建平台后写case；合成答案天然权威；留出集刷成开发集；格式正确/HTTP200即任务完成；只看文字不查终态；唯一黄金轨迹锁死合法路径；换Judge即无共同偏差；未运行或评分报错判通过；无限重跑删失败；pass^k等于用户一次成功率；对整体均值乘方；异步CI尚未完成就发布；固定基线偷偷换；所有探针命中都当事故；安全硬限只告警试跑；富集失败样本估全量率；批准=质量分；复制/退出天然正负标签；不满自动上传全会话；改评分器给自己刷分；小补丁回退无需查依赖。
